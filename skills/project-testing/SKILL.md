# Python 测试规范

以用户最新提供的《Python 测试规范 Skill》为依据。完整的 34 节规范保存在 [新版规范原文](references/python-testing-standard.md)，保留原文，不沿用上一份旧版测试规范。

## 读取方式

- 开始 Python 测试分析、编写、执行或审查前，先读取新版规范原文，并落实与本次任务相关的要求；本入口不能代替原文。
- 针对本仓库，再读取 [项目测试约定](references/project-context.md)，确认实际配置、测试目录、命令和数据边界。
- 先检查已有配置、fixture、helper、mock、测试数据与调用关系，不只读一个函数就机械生成测试；已有框架优先复用。
- 原文中的例子说明测试方法，不是本项目的业务契约，也不要求创建示例中的空目录或安装所有可选工具。

## 必须落实的规则

- 不默认相信 AI 生成的测试；测试代码本身必须审查，目标是发现真实缺陷。
- 先确定输入、输出、副作用、状态和预期依据。关键业务规则不明确时标记 `UNKNOWN_REQUIREMENT`，不擅自猜测。
- 重要功能考虑正常、边界、异常、非法输入、状态、依赖、并发和异步行为。按契约选择适用维度，不机械堆积用例。
- 具体断言返回值、关键业务数据、状态与副作用；API 测试同时验证状态码、响应字段、字段类型、认证和权限。
- 参数化减少重复；fixture 单一职责，共享程度决定放置位置，避免隐藏重要测试行为。
- Mock 外部依赖，真实执行被测逻辑；patch 对象实际被查找和使用的位置，不盲目 patch 定义位置。
- 文件用 `tmp_path`，数据库用测试或临时数据库；控制时间、随机性和异步任务，避免顺序依赖与共享可变状态。
- 对核心行为主动设计反例，判断合理的错误实现是否会失败。Hypothesis 和 Mutation Testing 根据实际需要使用，变异测试不是所有项目的必做项。
- 不以覆盖率数字判断正确性，重点关注分支、异常、边界和错误处理。未采集覆盖率如实说明。
- 失败先区分 Production Bug、Test Bug、Environment Problem、Test Data Problem、Requirement Ambiguity，并说明依据；不通过削弱预期或屏蔽失败获得绿灯。
- 发现产品缺陷时记录并保留复现测试；在修复任务范围内修复生产代码并回归，不为迎合测试随意改变业务行为。
- 实际执行后才能报告通过。报告按原文第 32 节列出文件、用例、结果、覆盖率、已测范围、缺陷、限制、未测风险和质量判断。
- 提交前逐项核对原文第 33 节自检清单。

## 在本项目应用

Python 后端沿用 pytest 和 pytest-asyncio；前端沿用 node:test，不因本规范更换框架。优先按 P0 核心、异常、边界，P1 模块交互、接口、一致性，P2 一般工具与非核心分支，P3 低风险代码分配测试资源。

使用项目现有环境执行相关测试；全量回归、覆盖率、真实依赖或变异验证按变更风险和任务范围选择。本次任务若仅创建或修改规范文档，检查规范格式、引用和内容即可，不因文档中的示例执行应用测试、访问正式数据或改变依赖。
