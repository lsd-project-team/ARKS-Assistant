# 执行环境与后续验收

应用计划部署到公司 Linux 服务器。Linux 容器执行通道与应用在同一台或管理员配置的 Docker context 上；业务项目所需的 Windows 环境独立准备。

| 部分                | 当前实现                                                             | 仍需准备/验证                                                                           |
| ------------------- | -------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Linux 应用          | 现有 Python/FastAPI、React 构建与 SQLite/附件存储                    | 公司服务器、账号、反向代理/TLS、数据与备份目录及恢复演练                                |
| Linux 隔离执行      | 可信固定镜像、无网络、受限资源、非 root 目标、路径校验回传           | 在目标服务器显式准备和探测镜像，按实际项目准备工具及离线依赖                            |
| ZX2200 Windows 执行 | 协议3适配、固定节点桥、容量准入与停止态传输已接入                    | 在独立Windows节点验收Hyper-V、ACL、SDK与实际构建镜像                                    |
| ZX2200 构建         | 只读扫描工程及依赖声明                                               | .NET Framework 4.8 targeting pack/SDK、MSBuild、NuGet 缓存、私有 DLL/授权和正确平台配置 |
| 业务验收            | 保存验收标准、基线、修改验证和审核版本                               | 实际项目构建/测试、已知问题回归、设备联锁/工艺与现场人员验收                            |
| 模型质量            | 有历史供应商报告；新增固定源码/模型/应用身份的独立评测和人工评审入口 | 用允许外发的真实问题及人工标准答案完成当前版本的供应商评估                              |

## 管理员准备流程

1. 在执行节点准备包含所需工具和离线依赖的受信任基础镜像，记录其 sha256。不要将业务仓库里的 Dockerfile 当作可信执行模板。
2. 使用 `scripts/execution/` 的准备命令包装本仓库 `resources/execution/` 模板。该步骤无网络，基础镜像必须已经存在；记录返回的实际镜像身份。
3. 在“系统配置 → 项目验证命令”选择项目，配置参数数组、容器平台、固定镜像、Docker context、类别和超时，手动探测环境。远端连接凭据由管理员保管在宿主，不注入沙箱。
4. 指定项目解决方案/工程、Configuration 和 Platform。先验证原版本，再修改并用相同配置验证。缺依赖、配置错误、代码编译失败和设备未接分别根据日志处理。
5. 核对当前差异、验收标准、基线和通过结果，再审核固定版本。下载交付包，在业务源码自己的分支检查应用，重新构建并回归；需要时按包内说明反向应用。

验证运行不会自动联网恢复包，不自动启动设备主程序，不自动改原业务源码。可信宿主配置仅用于明确受信任的人工测试，并始终标为非沙箱。

## ZX2200 的具体边界

当前只读扫描16个传统工程和2个解决方案，框架均声明 v4.8。根外依赖涉及本机 SDK/平台目录，另有一个源码根内缺失声明。327个无 HintPath 程序集声明还需由框架引用包、GAC或SDK解析；438个路径存在只证明文件可见，不能保证版本、授权或 ABI 正确。

本机 Windows 10 家庭版缺少可用 Windows 隔离构建节点，且未发现可用的目标 MSBuild 构建环境。已有本地.NET8 SDK用于自带Roslyn分析器，不等于ZX2200的.NET Framework 4.8工具链。公司服务器为 Linux，后续应准备独立 Windows 虚拟机或构建机并完成真实执行和构建验收；现阶段仍可阅读、修改副本和导出草稿。

Windows节点须专用于单个应用控制进程，不能配置多个uvicorn worker或多个数据实例同时控制同一节点。当前容量准入采用进程锁并拒绝其他owner的遗留容器，没有跨实例原子租约；共享节点和节点级硬配额不在已实现范围。详细协议、32位退出码和真实验收条件见[Windows适配](../architecture/windows-executor.md)。

Linux部署应显式准备分析器的.NET8运行时和自带helper；可配置 `ARKS_DOTNET_PATH` 与 `ARKS_ROSLYN_HELPER`。在backend目录运行 `python -m app.modules.source_analysis.setup --no-download` 使用现有SDK离线构建自带helper；正常源码请求不下载或构建。Roslyn目前使用自身.NET8基础引用并静态收集工程声明，不能代替ZX2200目标框架的完整语义绑定。

2026-10-19 已在本机 Docker Desktop 的 Linux 应用镜像中完成自带 helper 实际语义调用、域名登录、隔离编辑和独立卷恢复，见 [Linux运行验收](../verification/linux-runtime.md)。这不代表公司服务器已部署；静态知识资源的登录边界仍有已确认缺口，需要继续处理后再上线。

## 模型与业务评估

选取已知入口、主流程、一个已解决调试问题和一个明确新需求，分别由项目人员给出当前源码版本、正确调用路径/条件、适用环境、期望修改范围和验收命令。固定模型、参数、工具配置和问题文本后运行，记录：

- 引用是否对应当前文件版本、行号与实际条件；未知外部组件是否如实保留未知。
- 历史问题是否匹配设备、软件版本与工况；未解决记录是否被误当解决方案。
- 修改是否只在约定范围、能否复现旧问题、同环境基线与修改验证是否通过。
- 有无未读先断言、遗漏前置条件、假造已完成测试或设备结果。

由人工逐项判定，保存错误样例与版本，再用同样案例比较改进。新的[质量评估入口](../verification/code-work-quality.md)复用真实Agent，固定报告哈希、运行ID、源码和模型身份；自动机械事实不能自动提升为语义通过。历史报告不代表当前版本验收；本轮没有调用真实供应商完成这组质量验收，也没有完成 ZX2200 全仓模型阅读。

## 运维与数据

资源策略按项目持久化；token 日界使用 UTC，未知供应商用量不会自动退款。空间统计包括副本、临时输出及日志；创建/验证前检查额度与剩余空间，隔离进程另有硬资源限制。单台服务器总空间和所有项目合计用量仍需运维监控。

备份继续包含数据库和 scratch，恢复保留需求、审核、配置、额度和验证档案。备份包含业务源码与资料，应按公司保密规则存放。公司域名访问和镜像构建见 [Linux部署](../development/linux-deployment.md)。目前没有自动跨系统路径与源码身份迁移工具，不能只修改环境变量或批量替换数据库路径就宣称迁移完成；需先停服备份、在独立目录演练，明确旧根到新根的映射及源码摘要，再重新建立目标平台验证和审核。供应商凭据、执行context由管理员另行配置。
