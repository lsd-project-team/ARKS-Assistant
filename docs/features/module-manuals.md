## 图谱去重与主从关系

从本轮维护开始，功能与流程里的图谱按“一个主流程、一个细节入口”组织。同一业务的总览图只保留一个权威来源，按钮、分支和异常细节通过关联图进入，不再在两篇文档中各画一套完整主流程。

第一组已确定的主从关系是料单元系统：

| 角色 | 权威文档 | 保留内容 | 处理方式 |
|---|---|---|---|
| 总览与主流程 | `31-料单元系统全景与流程图.md` | 模块上下文、实体/配置树、Mapping 总体关系、数据流、落盘总览、风险总表 | 作为料单元系统的主入口 |
| 按钮与交互细节 | `43-料单元系统按钮与交互流程详解.md` | 具体处理器、前置条件、分支、异常、按钮后的最终效果 | 只保留按钮级增量；公共框架图引用 31 |
| 静态源码说明 | `19-料单元系统-界面层.md`、`20-料单元系统-模型与服务.md` | 控件、类型、字段和服务索引 | 作为源码查阅资料，不再作为第二套主流程入口 |

料单元系统中，以下主题以后只认 31 号的总览图：上下文、类型/实体树、Mapping 总关系、配置落盘总览和模块依赖。43 号仍保留按钮级图，但不得再复制这些总览图；按钮图应在标题或图注中标明对应的 31 号章节。

后续按同一规则处理固晶 32/33、晶圆 34/35 和标定 13/14/41。完成各组归并后，再重建目录索引和应用内图谱入口，避免先删资源导致旧链接失效。

固晶组已采用同一入口规则：32 号负责模型、动作节点和调度总览，33 号负责界面、按钮和交互细节。两篇仍保留各自专题图，但目录标题不再使用相同的“全景与流程图”表述；涉及完整生产链时先从 32 号进入，再按界面入口跳到 33 号。

晶圆组沿用同一规则：34 号负责模型、实体和调度总览，35 号负责界面与按钮细节。两篇的完整图仍分别保留，入口名称明确标出阅读层次。

标定组的入口层次也已明确：41 号是标定全景与主流程入口，13 号提供算法和数据模型说明，14 号提供界面与测试说明。三者不再使用相同的“全景流程”入口含义。

其余单篇图谱也统一使用“全景与主流程”作为入口层名称：36 号支撑特性、39 号物流搬运、40 号点胶和 42 号实验系统。对应的 11/12、18、21/24、16/17 继续作为专题或源码说明资料，不与主流程入口争夺同一名称。

- 区分 Pause、Stop 与 Working；急停先逐轴停止运动，再调用普通停止清理软件状态。
- 生产启动包含就绪检查、动作排序初始化和按配置启动任务，不简化成只改一个状态。
- 20 ms 为暂停等待的轮询间隔，不作为全局停机完成时限。
- 需料信号由固晶侧发往晶圆侧；修正整机循环的图文不一致。
- 修正启动摘要中的硬件初始化异常处理，并同步离线目录和搜索摘要中的旧表述。
- 修正原文中将 `WaitStart()` 暂停等待描述为直接返回 false 的相关段落。
- 修复原始详细流程图中的引号、转义、消息分隔符和括号格式，不新增业务节点或改变连线关系。

启停相关核对文件摘要保存在 `frontend/scripts/knowledge/manual-review.json`。其余正文保留原分析范围，本轮未逐条重新核对全部源码结论，也未进行设备验收。资料未新增 AI 检索入口。

## 维护与发布

正式资源唯一来源为 `resources/knowledge/flows/manuals/`，正文位于其 `docs/` 子目录。用户原始 `html页面/` 交付目录保留，不作为第二套运行资源。沿用 `/archify/` 的资源发布与正式会话访问控制。

修改正式资源后，在 `frontend/` 运行：

```powershell
npm run knowledge:manual-index
npm run knowledge:manual-check
npm run build
```

目录重建记录图解与正文摘要。标准构建核对全部资源、业务归类、默认章节、已核对启停源码摘要及全部详细流程图语法。资源使用固定 LF 换行，避免跨平台检出使摘要变化。

`repair-manuals.mjs` 保存已核实的交付 HTML 修正规则；`import-manuals.mjs <交付目录>` 用于首次导入，不应覆盖已维护的正式资源后直接发布。后续通常只重建目录与执行检查。
