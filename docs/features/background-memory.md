# 后台长期记忆

2026-10-29 起，长期记忆由后台从历史聊天提取、整理，供后续会话参考。聊天不再提供 `remember` 工具，设置页不再提供手动新增、编辑、删除和恢复记忆的入口。

## 生成与读取

1. 服务启动后每 60 秒扫描一次。默认选择最近 30 天内、已闲置至少 6 小时的聊天，每轮最多处理 16 个。
2. 候选需要至少两轮完整问答、累计至少 120 个正文字符。仍在运行、有等待发送问题、已删除、所属账号已禁用或项目访问归属不符的聊天不进入提取。
3. 只读取当前有效分支的完整成功问答。关闭长期记忆来源的问题、其他账号在共享聊天中的问题及对应回答不参与该账号的生成。
4. 提取模型生成少量稳定偏好、项目认识和工作方法。每条必须引用本次输入中实际存在的消息与连续原文；个人偏好只接受用户消息作为依据。长聊天分片处理，不静默丢弃尾部。
5. 提取结果先持久化，再由整理模型选择条目编号、归并主题。事实正文由程序从提取结果取回，整理模型不能改写正文或补造新的事实条目。
6. 完整文件写入后，数据库原子发布新快照。后续会话根据当前问题和选区路径，在当前账号、项目的有效记忆中筛选相关条目后带入。原聊天变化、删除或移动后，不再使用与其不一致的旧成果。

候选聊天的 30 天范围不意味着已发布记忆在 30 天后强制过期。已生成、原文及归属仍一致的记忆继续供后续会话和整理使用；标题等元数据更新不改变事实指纹。

后台独立于聊天执行槽位；失败不影响正常回答。生成使用发起账号选择的模型配置，可单独配置提取与整理模型。项目日模型额度不足时暂缓；供应商费用和用量未知时保留已有保守预留。后台不查询或声称掌握供应商账户的剩余额度。

## 按当前问题带入

2026-10-30 起，不再将整份项目记忆自动带入每轮回答。先验证当前账号、项目及来源聊天仍然有效，再以单条记忆的标题、正文和源码路径进行本地语义与关键词匹配，召回最多6条候选；检索输入不混入其他账号或项目。共用主题标题和原文依据不用于扩大主题匹配，以免同主题下的其他内容或原聊天中的旁支话题一起进入回答。

本地召回只建立候选，正式回答还需调用当前回答模型复核：结合当前问题、候选正文、原文依据和源码状态判断设备、版本、模块、工况及限制是否适用。模型只能返回已有候选编号，也可以全部不选；程序按编号取回固定版本原文，模型不能改写、补造正文。未知编号、重复编号、非法结构、超时或调用失败均不回退为未经复核的候选，本轮不带入记忆。

候选为空、没有明确问题、预算不足、关闭来源或只读取历史状态时不发起筛选调用。有候选时通常增加一次模型请求，过长时按完整条目分片复核，不截断适用条件；每次最多512输出token，整个模型筛选阶段最多30秒且不超过配置的请求时限，沿用现有项目额度回调并记录供应商实际用量。复核期间原聊天、记忆版本或已检查的源码状态发生变化时排除失效结果。

选中内容仍受可用输入额度的六分之一及8000 token上限约束。条目正文、适用条件、原文依据及来源作为整体装入，预算不足时跳过整条，不截断条件。本地语义模型不可用时仅使用关键词召回，再进行模型复核，不回退为全量记忆；问答中不下载检索模型。

运行上下文只记录实际选中的编号、正文及来源，保留固定版本供回看；私人筛选事件和记忆快照不向共享聊天中的其他账号暴露。设置里的长期记忆列表仍展示完整有效成果。检索和模型复核均可能误选或漏选，并非事实核查；选中的历史认识仍需按当前源码和条件核对。

## 状态和本地文件

设置 → 长期记忆展示当前账号在当前项目的记忆正文和更新时间，可刷新查看；页面不再展示后台提取说明、闲置筛选时间和处理数量。同页的“允许后台从闲置聊天提取和整理长期记忆”控制生成，由管理员保存配置；知识来源中的“长期记忆”控制带入，并控制对应问题能否成为后台输入。

生成成果按账号与项目隔离。即使管理员能查看同一项目，也不会从普通用户的记忆目录取得个人偏好。原回答的实际带入快照继续按原账号边界保留。

文件位于 `data/memories/automatic/<集合标识>/<内容指纹>/`：

- `memory_summary.md`：主题导航。
- `MEMORY.md`：整理后的记忆、原文及消息依据。
- `raw_memories.json`：本版本选中的结构化条目。

每个聊天的完整提取结果、输入指纹、重试与租约状态保存在 `memory_extractions`；已发布快照保存在 `memory_bundles`。数据库为读取依据，文件为可读投影。租约、输入指纹和发布版本用于防止重复处理、过期任务覆盖新成果和半份文件进入回答。服务重启后继续处理；整理失败时复用已经持久化的提取结果。

旧记忆文件在首次启动新版服务时移入 `data/memories/legacy-archive/`。旧版本表、正式聊天、问题与经验保持，旧记忆不作为新系统输入或新回答依据。备份包含归档与自动成果。

## 配置与边界

现有 `auto_memory` 开关控制后台生成；`memory_generation` 提供：

| 字段 | 默认值 | 用途 |
| --- | --- | --- |
| `idle_hours` | 6 | 聊天闲置时长 |
| `poll_seconds` | 60 | 扫描间隔 |
| `max_age_days` | 30 | 候选聊天时间范围 |
| `max_chats_per_pass` | 16 | 每轮最大处理数 |
| `min_completed_turns` | 2 | 最少成功问答轮数 |
| `min_remaining_percent` | 25 | 项目日模型额度的最低剩余比例 |
| `extract_model` | 空 | 提取模型，空时沿用摘要模型或当前模型 |
| `consolidation_model` | 空 | 整理模型，空时沿用摘要模型或当前模型 |

记忆仍然是历史线索。原文引用核查不能证明模型归纳必然正确，也不能代替当前源码核查和设备验证。关联源码变化时标明待复核；不训练模型，不恢复全项目阅读或项目资料检索。

该实现参考 OpenAI 官方的[本地记忆说明](https://learn.chatgpt.com/docs/customization/memories)与[配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)，采用后台提取、整理与后续带入的架构；项目额度、账号权限和具体筛选规则由本项目实现，不声称复刻 Codex 的全部内部算法。

真实供应商验证命令：

```powershell
backend/.venv/Scripts/python.exe scripts/verification/background_memory.py
```

该命令在临时目录中生成合成聊天，核对真实两阶段生成、后续带入和重复扫描复用；不发送正式聊天或修改正式业务记录。
