# 物流搬运系统（AKRS.ZX2200/TransportSystem）

> 整机基板流转的「物理流道 + 逻辑流道」双层实现：5 段皮带载台串成一条主线，两端可接上/下料仓（LoaderBin）或 SMEMA 联机送板机，段与段之间用 `SignalPool` 信号量握手。
> 代码规模：59 个文件 / 13,603 行（不含 `*.Designer.cs`、`*.resx`；全部 73 个 `*.cs` 均含设计器分部，本模块无可执行孤儿文件）

---

## 1. 模块定位

本模块只负责**把载具（`TransportUnit`）沿轨道从一端搬到另一端**，不负责固晶、点胶工艺本身。

在整机中的位置（`Main/Machine/MachineSupport/Machine.Operate.cs:276`）：

```

      → TransportModule.GetInstance().Init()      TransportDomain.cs:93   // 5 段皮带停 + 回零

      → LoaderTask.Start() / UnloaderTask.Start() TransportDomain.cs:126-127

```

- **上游**：`System1Domain.DispenseWorkTask`（点胶）、`System2Domain.BondTask`（固晶）通过 `SignalPool` 与本模块互相放行；上料端还有外部送板机（SMEMA）或 `LoaderBin` 料仓。
- **下游**：`TransportUnitSystem` 的 `TransportUnit`（载具实体，`TransportUnitSystem/` 由 19/20 号文档覆盖）；`ProductConfiguration`/`BondSystem` 会读 `BondSubSectionProgram.TransportUnit` 做工艺定位。
- **被谁调用**：`BondSystem`（`BondModuleController.cs:266` 等 4 处、`BondTask.cs:414`）、`DispenseSystem`（`DispenseWorkTask.cs:95`）、`CalibSystem/Controls/Assistant/FrmTransportTeach.cs:367-387`（示教时反找）、`Infrastructure/Controls/Feature/EditProgram/.../UcEditProductProgramming.cs`（程式编辑 UI 挂载本模块 9 个设置控件与 2 个示教窗体）、`Main/Controls/Ucmain/.../UcMainSystem.cs:870/1425`、`UcMainSystem.Manual.cs:262`（手动调试面板挂载）。

**本仓库不存在 `MoveTransportSystem/`、`MovePlatform/` 目录**；物流搬运 100% 落在 `AKRS.ZX2200/TransportSystem/`，硬件抽象（`Axis`/`Sensor`/`Electric`）在平台 DLL 中（无源码）。

## 5. 关键实现细节

### 5.1 状态机

只有**两个枚举、两层状态**，没有显式迁移表（`Models/Programs/BaseSubSectionProgram.cs:80-117`）：

- `SubSectionStateEnum`：`NoMaterial` / `HasMaterial` —— "这段皮带上有没有载具"。
- `SubSectionStateTransferEnum`：`Ready` / `Transfering` / `Alarm` —— "这段现在在不在传/是不是报警了"。

每段一个 `BaseSubSectionProgram` 实例（`TransportProgram.cs:27-47`），**5 段各自独立、无中央状态机**。迁移全部散落在 `TransportController` 各流程的首尾，典型模式：

```
入口先查 SubSectionState 不满足 → return ExcuteResult.NoStart
  → SubSectionTransferState = Transfering
  → 动作（气缸/皮带/传感器）
  → 成功: 改两段 SubSectionState + 两段 SubSectionTransferState=Ready + TransportProgram.Save()
  → 失败: SubSectionTransferState = Alarm + 弹框，用户选「忽略」则继续往下走
```

`ExcuteResult` 五值语义（`TransferAutoLoaderToLoading` 注释 `:438`）：`NoStart` 条件不满足下轮再试、`Success` 成功、`Abort` 退出工作、`None` 跳过这一片、`Exception` 异常。

**卡料/缺料/满料检测方式**（全部为"传感器 + 皮带停"二判据）：

| 异常 | 判据 | 位置 |
|---|---|---|
| 上料超时 | `Stopwatch > 5000ms` 仍无料 | `TransportController.cs:481` |
| 进料载台无料 | 皮带转完 `HasMaterialInModule()==false` | `:670` |
| 点胶载台卡料 | 皮带转完 `HasMaterialInModule()==false`（C 未感应） | `:734` |
| 点胶→Bond 卡料 | 皮带转完 `HasMaterialInOutlet()==false`（D 未感应） | `:1380` |
| Bond→等待段卡料 | 皮带转完 `HasMaterialInOutlet()==false`（E 未感应） | `:1620` |
| 出料等待载台卡料 | `E==true \|\| F==false` | `:1724` |
| 下料段卡料 | `G==false` 或 `G==true \|\| 等待段仍有料` | `:1894`、`:1977` |
| 下料仓推料失败 | `PushTabletToUnloader() != Success` | `:2173` |
| 上料仓缺料 | `IsOutOfTabletLimit() && CurBinType==BinB` → `IsLoaderEmpty()` | `LoaderBinController.cs:385`、报警 `:478` |
| 上料仓料盒缺失 | `IsCurrentBinOnTable()==false`（"前/后上料盒检测"传感器） | 报警 `LoaderBinController.cs:504` |
| 下料仓满料 | `IsOutOfTabletLimit() && CurBinType==BinB` → `IsUnloaderFull()` | `UnLoaderBinController.cs:328`、报警 `:431` |

**换仓逻辑**（`LoaderBinController.MoveToCurrentPlaceLayer():449` / `MoveToNextPlaceLayer():542`）：当前层超出 `LayerNum` 且当前是 BinA → 自动切 BinB 并重置层号 1；已是 BinB → 弹「上料仓已经没有料」[换仓/停止]，选换仓则 `ResetLoader()`（层号=1、料盒=BinA）后 `goto Reload`。注意 `MoveToCurrentPlaceLayer` 用 `MoveToNextBin()` 切仓（有实际 Y 轴移动），而 `MoveToNextPlaceLayer` 把 BinA 分支写成直接改 `CurBinType`（`:564`）——**Y 轴不会移动**，两条路径行为不一致。

### 5.2 同步模型：谁等谁

- **主握手用 `SignalPool`**（平台类，基于 `EventWaitHandle`）。本模块用到 9 个：
  `AllowLoaderMoveSignal`、`LoaderAllowPushSignal`、`AllowDispense1TransferToDispense2Signal`、`AllowDispenseTransferToBondSignal`、`AllowBondTransferToWaitingUnloadSignal`、`TransferToDispense1FinishedSignal`、`TransferToDispense2FinishedSignal`、`TransferToBondFinishedSignal`、`AllowUnloaderMoveSignal`、`UnloaderAllowPushSignal`。
  定义在 `AKRS.Galaxy2.Machine/Models/SignalPool.cs:74-124`；`LoaderAllowPushSignal` 与 `UnloaderAllowPushSignal` 是 `ManualReset`，其余为 `AutoReset`。
- `Signal.Wait()`（`AKRS.Galaxy2.Machine/Models/Signal.cs:116`）**先查机床状态**：`Stop` → 返回 `false`（流程主动退出）；`Pause` → 阻塞在 `WaitStart()` 里每 20ms 轮询（`Signal.cs:202-228`）。因此"暂停"对线程是阻塞式的，不是丢信号。
- **段内有料/无料用轮询标志位**，不是事件：各流程 `while(xxxController.IsMoving()) { 查传感器; Thread.Sleep(30~500); }`。
- **料仓与主线用双向信号串行**：
  `LoaderTask` 移层 → `LoaderAllowPushSignal.Set()`；`TransportTask` 推料完 → `LoaderAllowPushSignal.ReSet()` + `AllowLoaderMoveSignal.Set()`（`TransportTask.cs:412-415`）。下料侧完全对称（`TransportTask.cs:706-709` + `UnloaderTask.cs:92-117`）。
- **线程启动判据统一为 `task == null || task.Status != TaskStatus.Running`**（如 `TransportTask.cs:124`、`:211`、`:314`）——存在竞态：任务因异常退出后 `Status` 是 `Faulted`/`RanToCompletion`，下次启动会重建（这是设计意图），但旧线程若只是"暂停阻塞"则 `Status` 仍是 `Running`，不会重复启动。

### 5.3 异常处理约定

所有流程被 `try/catch(Exception)` 整体包裹，统一 `LogHelper.Post(Level.Error, ..., LogCategory.Transport)` + `AKRSXtraMessageBox.Show` 弹栈 + `return ExcuteResult.Exception`。**报警是模态弹框**（`AKRSMessageBoxExt.Show`），带 2~5 个按钮（重试/忽略/下一片/终止/不再上料），用户选择直接决定 `return` 值；`goto retry` 实现就地重试。异常分支**不回滚已改的状态**，唯一例外是 `TransferWaitingUnloadToUnloadBelt`（`:1818` 存 `stateTemp`、`:2038` 恢复）和 `TransferWaitingUnloadToUnloadBin`（`:2065`、`:2267`）。

### 5.5 安全与断电恢复

- **急停**：`Machine.Operate.cs:383` 对所有 `Axis` 并行 `StopMove(false,true)`，然后 `Machine.Stop()`。**流道线程没有被终止**——源码里明确留了注释：`// TransportDomain.GetInstance().StartTask(); 流道的Task线程不知道怎么结束`（`Machine.Operate.cs:398`）。只有 `DispenseWorkTask`/`BondTask`/`WaferSubSystemTask` 有 `AbortThread()`（`:399-401`）。流道线程靠 `Signal.WaitStart()` 在 `Stop` 态返回 `false` 自然退出，但若线程正卡在 `while(IsMoving())` 轮询或模态报警框里，则**不会退出**。
- **复位（Homing）**：本模块的"复位"= `TransportModule.Init()`（`TransportModule.cs:61`），只做 5 段皮带的 `StopMove()` + `BeltInit()`（`BaseSubSectionModule.cs:64` → `BeltAxisX.GoHome()`），并行执行后 `Task.WaitAll`。料仓的 Y/Z/推杆轴**不在 `Init()` 里回零**，由 `InitializeTS()` 的 `MovePushRodHome()` 只回推杆。
- **启动前拦截**：`Machine.Start()` 前要求 `AllAxisReset`（`Machine.Operate.cs:410`）、安全门关闭（`:223`）；`TransportDomain.StartTask()` 先跑 `CheckCarrierBeforeLoaderMove()`，出/入料口有载具时弹「不允许移动」并返回 `false`，随后 `Machine.Stop()`（`TransportDomain.cs:102-106`）。
- **断电恢复状态校验**：靠 `MapMaterial()` + `TransportDevicePara.IsReverseSearch`（默认 `true`，`TransportDevicePara.cs:59`）。反找流程 `SearchBelt()` 把皮带**倒转** `BackwardTransportDistance`，边转边看传感器，找到料就正转 `ForwardTransportDistance` 并 `Clamp()`；结果与 `TransportUnit` 记忆比对，4 种组合各弹一次「请确认是否真的存在载具」的 Yes/No（`BondSubSectionController.cs:429-605`、`DispenseSubSectionController.cs:437-523`）。**若 `IsReverseSearch=false` 且轨道上已有 TU 记忆，则直接跳过反找**（`:434-439`、`:440-445`）。
- 注意：`SubSectionState`、`SubSectionTransferState`、`TransportUnit` 三个字段都带 `[JsonIgnore]`（`BaseSubSectionProgram.cs:41-55`），`IsTuInDispense1` 亦然（`DispenseSubSectionProgram.cs:66`）。即**轨道有料状态不落盘**，`TransportProgram.Save()` 实际只持久化配置类字段（`TransportBeltSettingName`、`BondSubSectionProgram.Size` 等）与 `LoaderBinProgram.CurPlaceLayer`/`CurBinType`。断电后"记忆"必须靠 `MapMaterial()` 重建——这与代码里"不能记忆已经生产的信息"的提示语（`TransportController.cs:170`）措辞不一致，以代码为准。

### 5.6 并发与锁

- 主线并发：`TransportTask.Start()` 一次拉起最多 8 条 `Task.Run` 长循环（`TransportTask.cs:127/213/316/434/472/557/613/666/731`），每条独立线程名（`CommonUtil.SetCurrentThreadName`），互相之间**只靠 `SignalPool` + 共享的 `TransportProgram` 状态字段**协调，没有任何锁。
- `BondSubSectionController` 的加热相关方法（`OpenHeater`/`CLoseHeater`/`SetHeaterTemperature`/`GetHeaterTemperature`/`Alarm`/`IsHeatingSucceed` 等，`:812-1030`）用静态锁 `obLock`（`:889`）串行化，且每个方法内先 `Thread.Sleep(50)` 再访问硬件——持锁睡眠，UI 线程调用时会卡界面。
- `FrmTransportSystemProductLocation` 用 `static object Lock`（`:37`）做单例双检。

## 8. 注意事项与风险

### 8.1 逻辑缺陷（读代码发现，未实测）

1. **`TransferWaitingUnloadToUnloadBelt` 的 H 传感器判断失效**（`Controllers/TransportController.cs:1956-1977`）。`bool hasMaterialInUnloading` 在 `:1962` 被赋值，此后从未被读取；`:1977` 的条件是 `hasMaterialInFeedingInletUnload == true || hasMaterialInOutletWaitingUnload == true`，而注释写的是"如果 G 感应到 或者 H 没感应到 报警"。对非 `Belt` 配置，`hasMaterialInFeedingInletUnload` 是上一段循环（`:1935`）遗留的值，若 `:1933` 的 `while(IsMoving())` 一次都没进（皮带已停），它仍是 `true` → **每次都会误报"下料等待载台卡料"**。编译器应有"变量已赋值但未使用"警告。
2. **`BondSubSectionModule.HasMaterialInModule()` 抛 `NotImplementedException`**（`Modules/BondSubSectionModule.cs:109-112`），且它经 `BaseSubSectionController.HasMaterialInModule()`（`BaseSubSectionController.cs:88`）对 `BondSubSectionController` 公开。当前全仓库无调用点（已 grep 确认），但任何人写 `BondSubSectionController.HasMaterialInModule()` 都会直接崩。
3. **`BondSubSectionController.OpenVacuumAndCheck()` 是忙等且无下限保护**（`Controllers/BondSubSectionController.cs:725-740`）：`while (sw.ElapsedMilliseconds < CheckVacuumTime) { if (CheckVacuum()) return true; }` 循环体内**没有 `Thread.Sleep`**，100% 占一个核；且若 `CheckVacuumTime <= 0` 循环体一次不执行，直接 `return false`。
4. **`TransportTask.IsAlive()` 在 `LoaderBin` 配置下必然返回 `false`**（`Tasks/TransportTask.cs:913-925`）：判据里包含 `this.transferLoadBeltToDispense1Task != null`，而该字段只在**非** `LoaderBin` 分支（`:211`）里创建。唯一调用方是 `FrmSignalDisplay.cs:75`，即诊断面板上"流道线程状态"灯在料仓机型上永远显示异常。
5. **`MoveToNextPlaceLayer` 切料盒不移动 Y 轴**（`Controllers/LoaderBinController.cs:561-566`）：BinA 用尽时直接把 `CurBinType = BinB` 后 `goto Reload`，而 `MoveToCurrentPlaceLayer` 的同类分支（`:465-473`）走的是带 Y 轴移动的 `MoveToNextBin()`。`UnLoaderBinController.MoveToNextPlaceLayer():513-518` 同病。后果：切仓后 Z 轴在新料盒的层高上动作，但 Y 仍在旧料盒位置。**疑似 bug，需现场确认是否被 `MoveToCurrentBin()` 兜住**（`Reload` 后会调 `MoveToCurrentBin()`，见 `:553`）——若被兜住则是"多一次 Y 空移"，否则是撞料盒。
6. **`UnLoaderBinController.MoveToCurrentPlaceLayer()` 缺"推杆安全"前置检查**（对比 `LoaderBinController.cs:449-462` 与 `UnLoaderBinController.cs:402-415`）：上料侧进 `MoveToTabletLevel` 前有 `IsPushRodSafe()` 保护，下料侧 `MoveToCurrentPlaceLayer` 直接调 `MoveToTabletLevel`，只在 `MoveToTabletLevel` 内部（`UnLoaderBinController.cs:205`）才检查。
7. `TransportTask` 中 `case ExcuteResult.NoStart: Thread.Sleep(500); continue;`（`:385-388`）跳过了循环尾部的 `LoaderAllowPushSignal.ReSet()` 与 `AllowLoaderMoveSignal.Set()`（`:412-415`）。由于 `LoaderAllowPushSignal` 是 `ManualReset`，下一轮 `Wait()`（`:375`）会立即返回，形成 500ms 周期的空转；同理 `:691-694`。
8. `TransportController` 里私有属性 `transportProgram`（`:97`）与公有属性 `TransportProgram`（`:57`）仅靠大小写区分，且 `:57` 是 `public TransportProgram TransportProgram => TransportProgram.GetInstance();`（同名类型/属性，靠 C# color-color 规则解析）。可编译，但极易写错。
9. `BondSubSectionModule` 的 `TrackFrontCylinder2PLSensor`/`TrackBackCylinder1PLSensor` 等 4 个传感器（`Modules/BondSubSectionModule.cs:82-97`）指向 `固晶区压料气缸动点升起检测2/3`、`原点下降检测2/3`，这些名字**不在 `GetHardWareNames()` 里**（`TransportController.cs:2621-2628` 被注释掉，注明"新设备没有"）。夹紧/松开检查里有 `== null ||` 兜底（`BondSubSectionController.cs:183-186`、`:273-276`），所以只是"永远跳过"。
10. `DispenseSubSectionModule.点胶区负压检测`（`Modules/DispenseSubSectionModule.cs:110`）声明后全仓库无引用，且 `GetHardWareNames()` 未登记 → 死代码；且它是唯一一个**没有 null 兜底**的硬件属性（其余限位传感器都有），一旦被调用而硬件不存在会直接 `NullReferenceException`。

### 8.2 硬编码与配置风险

- **113 处 `Thread.Sleep`，无一处走配置**。除气缸延时（`BondinsertSetting` 的 4 个 Delay）外，传输过程的等待/超时全是字面量（清单见 5.4）。特别是 `:481` 的 5000ms 上料超时和 `:1063` 的 10000ms 推杆缩回超时，换板型/换送板机时必须改代码。
- **推杆缩回的"退料位"是硬编码数字，不是示教值**：上料 `MovePushRod(2)`（`Controllers/LoaderBinController.cs:97`）、下料 `MovePushRod(4)`（`UnLoaderBinController.cs:92`），注释仅写"去这个位置是防止触发限位"。而推料位是示教来的（`LoaderBin.PushPos`）。两个数字在不同机型上是否通用未经核实。
- **推杆"安全"判据阈值硬编码且两侧不一致**：上料 `Math.Abs(GetRealPosition()) < 2.5`（`LoaderBinController.cs:400`），下料 `< 5`（`UnLoaderBinController.cs:342`）。同样含义用两个不同阈值。
- **`IsLoaderEmpty()` / `IsUnloaderFull()` 定义了但几乎没用**：`LoaderBinController.IsLoaderEmpty():385` 全仓库无调用（缺料判定实际走 `MoveToCurrentPlaceLayer` 内部逻辑）；`UnLoaderBinController.IsUnloaderFull():328` 同样。属于"预留但没接上"的 API。
- `LoaderBinController.MovePushRod(pos)`（`:76`）与 `UnLoaderBinController.MovePushRod(pos)`（`:73`）在失败时 `throw new Exception`，而 `MovePushRodHome()` 是 catch 后返回 `ExcuteResult.Exception` —— 同类操作两种错误约定。
- `LoaderBinController.IsLoaderEmpty` 逻辑是 `IsOutOfTabletLimit() && CurBinType == BinB`，但 `IsOutOfTabletLimit()` 也覆盖 `CurPlaceLayer <= 0`；`SetCurPlaceLayer(0)` 在 `MoveToNextPlaceLayer:565` 被主动调用，与"序号从 1 开始"（`LoaderBinProgram.cs:32` 注释）冲突。

### 8.3 并发与安全

- **急停不终止流道线程**（`Main/Machine/MachineSupport/Machine.Operate.cs:398` 注释明说）。`EmergencyStop()` 只对轴 `StopMove` 并切 `MachineStateEnum.Stop`；流道 8 条线程靠 `Signal.WaitStart()` 自查状态退出。**若线程阻塞在模态报警框（大量 `AKRSMessageBoxExt.Show` 无超时）或 `while(IsMoving())` 轮询中，急停后仍在跑**。
- **`TransportProgram` 的多线程写入无锁**：8 条流道线程 + `LoaderTask`/`UnloaderTask` 都会写 `TransportProgram` 各字段并调 `Save()`（如 `TransportController.cs:529`、`:1503`、`:1787`、`:2262`），`Save()` 由平台 `Singleton<T>` 实现（无源码），是否线程安全未知；多个线程并发 `Save()` 同一文件也可能造成 JSON 写坏。
- **暂停是阻塞式**：`Signal.WaitStart()`（`Signal.cs:217-225`）在 `Pause` 态死循环 `Sleep(20)`。暂停时点「停止」能退出（`:219` 二次判断），但暂停时点「急停」若线程在此之前已进入 `WaitOne` 之外的分支，退出时机不确定。
- **`UnloaderTask` 比 `LoaderTask` 多一个 `IsPause()` 检查**（`Tasks/UnloaderTask.cs:69-73` vs `Tasks/LoaderTask.cs:74-96` 无此检查）——不对称，同一暂停场景下上料仓线程行为可能不同。

### 8.4 死代码 / 一致性

- `Tasks/TransportTask.cs:48-50` `transferLoadBeltToBondTask` 字段注释"上料皮带传到Bond,弃用"，全类无任何使用。
- `Tasks/TransportTask.cs:431-433` 注释"本次节点先不用， 下一迭代 加上"。
- `BondinsertSetting.VacuumOption`（`BondinsertSetting.cs:82-85`）注释"此参数暂时没用"，特性被注释掉。
- `Controls/Manual/FrmTransportSystemProductLocation.cs`（190 行）**唯一启动点在 `TransportDomain.cs:131` 被注释掉**，全仓库无其它引用 → 编译进程序但不可达。
- `Models/TransportDomain.cs:143-153` 有一整段被注释的 `IsTranportSystemReady()` 方法（且缺少 `return`，若启用无法编译）。
- `Controllers/LoadingSubSectionController.cs:61`、`UnloadingSubSectionController.cs:63`、`WaitingUnloadSubSectionController.cs:63` 三处 `SearchBelt()` 全是 `throw new NotImplementedException()`，而 `MapBelt()` 会调用它（`UnloadingSubSectionController.cs:73`、`WaitingUnloadSubSectionController.cs:73`）→ **这三段的 `MapBelt()` 一旦被调用必然抛异常**（当前只有点胶/Bond 段的 `MapBelt` 会被调，见 `TransportController.cs:135-139`）。这是最危险的"定时炸弹"：将来给下料段加反找功能时会直接崩。
