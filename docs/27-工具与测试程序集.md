## 4. 核心流程

### 4.1 `Akrs.ChangeJson` —— 唯一有实际工程价值的工具

它解决的是这样一个问题：**参数 JSON 里序列化的 `"type": "命名空间.类名, AKRS.ZX2200"` 在类改名/换命名空间后全部反序列化失败**。工具通过反射当前编译出的 `AKRS.ZX2200.exe` 重建"类名 → 当前命名空间"映射，再批量改写磁盘上的 JSON。

## 5. 关键实现细节

### 5.1 五个工程共用的"反模式三件套"

| 现象 | 位置 | 后果 |
|---|---|---|
| `RootNamespace`/`AssemblyName` 仍是模板名 | `InterpolationMovementTest.csproj:9-10`（`WindowsFormsApp1`）、`Akrs.ChangeJson.csproj:10-11`（`DXApplication1`） | 产物名与工程名完全无关，找 exe 时容易漏 |
| `ProjectGuid` 与 `AssemblyInfo` 的 `Guid` 不是一回事，且跨工程重复 | `Akrs.ChangeJson/Properties/AssemblyInfo.cs:Guid("9006f149-…")` 与 `AKRS.Galaxy2.Component.TestDemo/Properties/AssemblyInfo.cs:Guid("9006f149-…")` **完全相同** | 两个不同程序集有同一 `GuidAttribute` |
| `References` 整份拷贝、从不清理 | `InterpolationMovementTest.csproj` 54 条引用中**实际只用 5 条**（`AKRS.Galaxy2.Drive`、`AKRS.Galaxy2.Infrastructure`、`AKRS.Galaxy2.LogicHardware`、`AKRS.Galaxy2.MachineSupport`、`dsa40net` + DevExpress）；其中 38 条与 `AKRS.Galaxy2.PR.Test` 的引用清单重合 | 编译期拖入大量无关 DLL，构建变慢、版本冲突面变大 |

### 5.2 两个工程声明为 `Library`，所以**双击不能运行**

- `AKRS.Galaxy2.TeachTest.csproj:8` → `<OutputType>Library</OutputType>`，且 `:39` 的 `<StartupObject />` 是空的。`Program.cs` 里**有** `Main`（`Program.cs:16`），但产出是 `.dll`。VS 里把它设为启动项目会直接报"不能直接启动类库工程"。
- `AKRS.Galaxy2.RealtimeCurve.TestDemo.csproj:8` → 同样是 `Library`，`Program.cs:17` 也有 `Main`。

要运行这两者，必须先手工把 `OutputType` 改成 `WinExe`。

### 5.3 `InterpolationMovementTest` 的三处硬编码

1. **平台目标自相矛盾**：`InterpolationMovementTest.csproj:18` Debug = `x64`，`:29` Release = **`AnyCPU`**。而它引用的 `dsa40net.dll`（ETEL，`processorArchitecture=AMD64`）是 64 位原生库 —— 出 Release 版会 `BadImageFormatException`。（与主程序同一个坑，见 `29-外部依赖与二进制资产.md` §8.3。）
2. **PVT 两轴的轨迹是写死的常量**：`Movements.cs:887-927` 直接 `new DsaVector(10.0e-3, 0, 0, 0)` / `velocity.set(50.0e-3, …)`，与界面上 5 个示教点**毫无关系**。真正读 `movePositions` 的那段（`:944-977`）被整段注释。`PTWithTwoAxis` 更极端：`Movements.cs:1047-1048` 一进来就把 BondX/BondY 抬到绝对位置 0。
3. **`MovePositions` 的落盘路径**：`MovePositions.cs:22` → `Path.Combine(PathConfig.DeviceDirPath, "PVTMovePositions.json")`。该文件**不在仓库里**，只能由本工具运行时生成。也就是说**首次运行前 5 个点全是默认值（0）**。

### 5.4 `AKRS.Galaxy2.LogTest` 与 `AKRS.Galaxy2.Log.TestDemo.exe` 是两套东西

我解了两份二进制的字符串表，结论明确：

| | 工程 `AKRS.Galaxy2.LogTest`（本仓库源码） | `AKRS.ZX2200/libs/AKRS.Galaxy2.Log.TestDemo.exe`（厂商预编译） |
|---|---|---|
| 程序集名 | `AKRS.Galaxy2.LogTest`（`AssemblyInfo.cs` `AssemblyTitle`） | `AKRS.Galaxy2.Log.TestDemo`（exe 内 `AssemblyTitle`） |
| 主窗体类 | `AKRS.Galaxy2.LogTest.FrmLogTest` | `AKRS.Galaxy2.Log.TestDemo.FormLogTestDemo` |
| 按钮/开关 | `BtnAnomalies`、`BtnLogs` | `BtTestLog`、`BtTestLogException`、**`ChkIsLogInfo`、`ChkIsLogWarn`** |
| 引用的平台类型 | `AKRS.Galaxy2.Log.Control.UcLogControl`、`LogsManager` | 同样用 `AKRS.Galaxy2.Log.Control` 与 `AKRS.Galaxy2.Infrastructure` |
| 是否随安装包发布 | **否** | **是**（见 §6.1） |

结论：**本工程是厂商原版 demo 的重写版**。最直接的证据是原版把 `IsLogInfo`/`IsLogWarn` 做成复选框（`ChkIsLogInfo_CheckedChanged`），而本工程把它们**写死成 `true`**（`FrmLogTest.cs:19-20`）。

另一件佐证：`AKRS.Galaxy2.Log.dll` 自身就自带日志查看控件 —— 其字符串表含 `AKRS.Galaxy2.Log.Control.UcLogControl`（配套 `BtnPause_Click`、`BtnContinue_Click`、`BtnLogClear_Click`）与 `LogsManager`。所以 LogTest 工程本身没有新增平台能力，只是换了个壳。

`Log4Net.config` 的归属存疑：工程内这份 544 行（21,146 字节），而运行目录里的 `bin/Debug/Log4Net.config` 是 27,777 字节，`AKRS.ZX2200/SupportFeature/Logs/Log4Net.config` 是 22,594 字节 —— **三份内容互不相同**。并且 `AKRS.Galaxy2.LogTest.csproj:89` 是 `<None Include="Log4Net.config" />`，**没有 `CopyToOutputDirectory`**，所以它根本不会被复制到输出目录；同时 `AKRS.Galaxy2.LogTest/App.config`（13 行）里也**没有 `<log4net>` 配置节**。平台库 `AKRS.Galaxy2.Log.dll` 的字符串表里同时出现 `XmlConfigurator` 与 `ConfigurationManager.OpenExeConfiguration`，说明它既可能读 `<exe>.config` 也可能读独立文件，**具体走哪条路无法从可读源码确证**（见 §8）。

### 5.5 `AKRS.Galaxy2.Component.TestDemo` 与两个平台程序的三角关系

| 文件 | 是什么 | 依据 |
|---|---|---|
| `AKRS.ZX2200/libs/AKRS.Galaxy2.Component.Simple.dll` | **组件工具箱**，不只是曲线：内含 `MoveControl`(`UcMoveControl`/`FrmMoveControl`)、`AngleCalibration`、`AnnularLimit`、`FileCleaner`、`ImageView`、`LogHistory`、`MeasuringControl`、`MessageBox`、`PixelCalibration`、`SearchFirstDie`、`Statistics`、`CommonControls` | DLL 字符串表命名空间清单 |
| `AKRS.ZX2200/libs/AKRS.Galaxy2.Component.Test.exe` | **厂商原版运控演示**：类 `AKRS.Galaxy2.Component.Test.Form1`，窗体里放 `UcMoveControl`，并调用 `InitAllHardware`、`HardwareRepositoryService`、`AxisConfig`、`HardwareInitResult` | DLL 字符串表 |

### 8.2 `AKRS.Galaxy2.TeachTest` 的两处"看起来能跑其实不动"

1. **窗体是 `Library` 产物**（§5.2），不能直接运行。
2. **`DoneAction` 里对 `stepIndex` 的额外自增没有被 `SetUiControl` 收尾**。`FrmSubstratePositionTeachTest.cs:550-554` 与 `FrmModulePositionTeachTest.cs:465-469` 的 `BtDone_Click` 都是先调 `DoneAction()`、再 `stepIndex++`；而这两处的 `DoneAction` 内部**自己又加了一次**（`FrmSubstratePositionTeachTest.cs:265`、`FrmModulePositionTeachTest.cs:193`），于是索引跳 2。`FrmTUPositionTeachTest.cs:370-375`、`FrmModuleAdjustTeachTest.cs:246-250`、`FrmTUAdjustTeachTest.cs:239-244`、`FrmSubstrateAdjustTeachTest.cs:270-274` 则**连 `SetUiControl` 都没调**，界面会停在旧描述上。这不是设计，是 6 份复制粘贴各自演化出的不一致。

### 8.3 `Akrs.ChangeJson` 会**无条件覆写**输入目录下所有 JSON

`BtUpdateJson_Click`（`UcChangeNameSpace.cs:132-181`）的四个问题：

1. **无备份、无确认、无 dry-run**：`File.WriteAllText(filePath, content)`（`:178`）在 `foreach` 内无条件执行，即使一个 `Match` 都没有，文件也被原样重写（换行/编码可能变化）。这是**不可逆的批量原地修改**。
2. **按类名精确匹配，重名即错**：`:153` 用 `ClassNameSpaceList.Find(a => a.ClassName == className)`，只比类名不比旧命名空间。若两个旧命名空间下存在同名类，会挑到列表里第一个，**静默把 JSON 改到错误的命名空间**。
3. **只改应用内命名空间，不改程序集尾缀**：`:170` 的替换串仍以 `, AKRS.ZX2200"` 结尾（§4.1）。
4. **跨线程 `Invoke` 阻塞 + `Assembly.LoadFrom` 后果未知**：`:88-89` 用 `LoadFrom` 把主程序 exe 和 `AKRS.Galaxy2.Infrastructure.dll` 载入本进程；若两侧依赖版本不一致，可能抛 `ReflectionTypeLoadException` 而 `:92` 的 `GetTypes()` 没有 try/catch。同时 `this.Invoke(...)`（`:156`、`:164`）是从 `Task.Run` 后台线程同步回 UI 线程，逐条匹配逐条封送，JSON 多时界面会卡。

**正确用法**：只在**离线的、已备份的**参数目录上跑；先在测试目录上验证一遍再上现场。
