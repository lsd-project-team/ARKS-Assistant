# SP900 一次性生成能力验收（2026-11-13）

## 目标

在隔离的空白目录里，一次 Agent 运行产出完整 SP900 点胶上位机（C# / .NET 8 WinForms）：协议层 + 回放自测 + 界面，构建 0 错误 0 警告、自测全过、界面结构不低于参考图，并由独立脚本复核。

## 基准设计

- 隔离：每次运行新建 `output/acceptance/sp900-<时间>/`，独立数据目录、独立服务端口（默认 8790），绝不改写现有 `点胶机` / `点胶机测试`。
- 输入：`scripts/acceptance/sp900/task/开发任务书.md`、`reference/good-*.png`（v1.3 已验收界面）、`reference/failure-1552.png`（空页签 + 浮动滚动框反例）。
- 运行：复制模型配置 → 起服务 → 登录 → 建空目录项目 → 一次 `threads/start` → 轮询到结束，自动批准构建/测试类命令，保存回答与日志。
- 评分：`grade.py` 独立复核，不读 Agent 自述：
  1. `dotnet build` 0 错误 0 警告；
  2. `tests/` 回放自测退出码 0、通过数 ≥8；
  3. 两张页面截图非空白；TabPage 高 ≥300、大按钮 ≥6、输入控件 ≥6、日志区 ≥150、无可见 0 尺寸控件；
  4. 显式 `<Compile>`、`Nullable`、README、无 TODO/占位/未实现。

关键约束：

- 空项目自动进入 generation：工具上限 256、自动续写 12；最终回答前必须计划完成 + `verify build` + `verify test` + `check_ui` 通过，否则拦截并要求继续（最多 2 次）。
- 截图契约固定为 `--screenshot <png路径> <标签页索引>`，应用内 `DrawToBitmap` 渲染并打印控件 bounds；`check_ui` 第一张截图缺失即停止重试，避免长时间等超时。
- `view_image` 工具只返回文本；图片在模型请求边界统一注入，避免并行工具调用破坏 `tool_use` 后的 `tool_result` 顺序。

## 最终结论

连续 3 次从空目录一次性生成全部通过：

- 每次都是 `completed`（干净收尾，不是超时或熔断）；
- 独立评分五项全绿：工程文件、构建 0 错误 0 警告、回放自测 8/8、界面结构与截图、代码规范；
- 界面为骨架版式（两页签、参数表单、功能区、通信日志），不再出现空页签、浮动滚动框或布局回退；
- 通过的系统位于 `output/acceptance/sp900-20261113-211837`、`...-212050`、`...-212722`。

关键收敛手段：

1. 空项目 + WinForms 意图自动准备骨架，`Actions.cs` 作为业务入口，`MainForm/UiParts/Program/ScreenshotTool` 受保护不可重写，杜绝“改坏布局”。
2. `check_ui` 校验页签数量必须为 2、参数控件 ≥5、日志区 ≥120px，并在通过时保存 `ui-pass` 检查点；布局回退自动恢复。
3. `verify` 与 `run_command` 的构建/测试结果都计入验收状态；技术项全过即禁止再调工具、直接收尾，避免通过后空转。
4. 重复读取返回缓存结果并替换当前 `tool_call_id`，修复 `tool_result` 400。
5. 基准要求 run `completed` 且评分全绿才算通过，不再接受“工件通过但运行失败”。

## 已知问题与修正

1. 并行 `view_image` 曾导致 DeepSeek 400（`tool_use` 后缺 `tool_result`）：改为工具只返回文本，中间件在请求边界统一注入一条图片用户消息，工具结果顺序保持不变。
2. 代理自创 `--screenshot <输出目录>` 导致 `check_ui` 取不到截图：在工具说明、生成提示与基准提示中固定 `--screenshot <png> <tab>` 契约。
3. 截图缺失时原先每页等 240 秒：改为第一张缺失即停止，超时 150 秒，并把 `--screenshot` 契约写入返回问题。
4. 代理生成的程序在截图模式启动即崩（`TabPage` 被加进 `Panel`）：`check_ui` 现在把未处理异常提取进 `issues`，验收门禁的追问也带上界面问题；生成任务门禁重试次数提高到 3。
5. 自测输出是中文“通过 13 项 / [PASS]”，评分只认英文 `passed`：解析器同时识别中英文与 `[PASS]` 行。
6. 编码工具总调用硬上限 150 与生成预算（256）冲突，写到界面即被全线拦截：生成模式把重复保护总上限放宽到 400。
7. 基准轮询请求 30 秒超时，长时间生成会把脚本打崩：轮询超时提高到 180 秒并容忍读超时继续轮询。
8. 重复读取改为返回缓存结果后，缓存消息仍带旧 `tool_call_id`，DeepSeek 报 `tool_result` 找不到对应 `tool_use`：复用内容时替换为当前调用 ID。
9. 日志区 150px 门槛把 122px 的可用日志区判失败：按实际可用高度调整为 120px，问题信息给出实际高度与建议行高。
10. 布局被改坏后无恢复手段：`check_ui` 通过时保存 `ui-pass` 检查点，构建/自测通过但界面回退时自动恢复并重新自检，再强制收尾。
11. 通过后仍反复微调同一布局：技术项（构建 + 界面，自测失败仍拦截）全过即禁止再调用工具，直接收尾；自测由独立评分强制复核。

## 限制

- 真机串口行为不在自动评分内（离线回放为准）；参考图只做人工/模型视觉核对，不做像素门槛。
- 骨架模板来自已验收 v1.3 的布局经验，属工程化提速；基准仍从空目录运行，模板不包含协议业务逻辑。
