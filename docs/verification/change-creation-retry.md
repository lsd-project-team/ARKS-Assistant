# 同一修改请求的创建重试与恢复

2026-10-19，继续完善[原始需求绑定](request-binding.md)。旧实现允许同一请求重复创建隔离副本，重新填写更宽的范围或更低的验收要求；原副本的约定虽不能被直接改写，模型仍可能绕到另一份副本继续。修改前的两个真实临时副本反例失败，JUnit 在本地 `output/creation-retry-before.xml`，分类为 Production Bug。

## 修改后的行为

- 同一项目、同一服务端用户消息身份、同一原始请求正文对应已有副本时，创建重试直接返回它。中断恢复/重新生成的 run ID 不同，也不能重置副本。工具明确返回 `reused: true` 和说明，忽略本次重复创建参数，沿用当前约定、文件差异和验证档案。
- 合法人工修订后的约定继续生效；不会回滚为最初的约定，也不会用重试参数覆盖它。已丢弃或按保留规则清理的副本不会因模型重试而重新出现，需要新的用户修改请求。
- 新用户消息、用户实际改写后的问题、其他项目和页面人工创建仍各自独立。同一消息的旧记录若已有多个副本，稳定选择最早记录，保留历史，不删除或重写其他记录。
- 身份来自服务端消息，不接受模型传入重试键。直接构建工具且没有消息身份时，只在该工具实例内记住首次创建的副本，不伪造消息 ID；实际聊天还会从持久化原始绑定查找，重新打开数据库后仍有效。
- 检查和创建沿用项目编辑锁及 CodeChanges 服务锁。部署仍遵守单服务、单进程、单数据目录约定；没有新增跨进程租约或多 worker 支持。没有数据库迁移，也没有将来源不明的老记录猜测成某次人类请求。

这项修复约束的是同一请求的重复创建。首次约定仍由模型整理，不能据此保证任意自然语言已被完全理解或自动批准业务范围；后续人工业务评审和原始源码只读边界保持不变。

## 验证范围

新增测试 `backend/tests/integration/agents/test_change_creation_retry.py` 实际使用临时文件、SQLite、真实项目/消息/恢复记录、Agent 图和本地验证进程，只替换外部供应商模型。用例覆盖：

1. 已修改文件后以更宽范围/清空验收再次创建，仍返回原副本及原约定。
2. 并发工具实例创建同一用户消息，只产生一份副本；断言不依赖锁的先后顺序。
3. 关闭数据库再打开，重试保留人工更新后的验收和完整原始绑定。
4. 已丢弃副本不能被恢复创建。
5. 新问题、实际编辑的问题、页面手动创建与其他项目保持独立。
6. 缺少消息身份的直接工具实例仍不会重复创建。
7. 实际执行检查副本入口的 Python 命令后重试，验证 ID、日志、退出码及版本不变；原件仍为 Main。
8. 通过真实 Repository.resume 与 Agent.execute 恢复运行，测试模型主动请求清空验收、约束和路径；返回现有副本，保留 Start 的修改，原始消息/初始 run 身份不变，不产生假验证或人工审核。

以上是控制和数据一致性验收，不是新的真实供应商质量结论。本轮没有再次调用外部模型，也没有额外外发正式代码或资料。上一轮网格业务案例的模型报告与指纹保留，不能冒充本批代码的又一次真实模型运行。
