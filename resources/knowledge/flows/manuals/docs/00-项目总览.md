## 1. 这台设备是做什么的

ZX2200 是**半导体后道封装的固晶机（Die Bonder）**：把晶圆（Wafer）上切好的裸芯片（Die）逐颗拾取，经点胶（Dispense）、PR 视觉对位（Pattern Recognition），精确贴装到基板（Substrate/Lead Frame）的固晶位上，再经检测、收料完成一个循环。

整机的物理子系统与代码模块一一对应：

| 物理子系统 | 代码模块 | 职责 |
|---|---|---|
| 晶圆台 / 顶针 / 上视相机 | `WaferSubSystem/` | 晶圆图管理、芯片拾取点定位、顶针升降 |
| 固晶头 / 焊头 / 力控 | `BondSystem/` | 取芯片、PR 对位、贴装、压力/力控、测高 |
| 点胶头 | `DispenseSystem/` | 基板点胶（时间-压力式） |
| 物流搬运 | `TransportSystem/`、`TransportUnitSystem/` | 料匣/基板在工位间的搬送、上下料、Mapping |
| 标定 | `CalibSystem/` | 相机-轴坐标映射、二维补偿、精度验证 |
| 实验 / 精度测试 | `Experiment/` | 位置精度、贴装精度、重复定位精度等测试 |
| 支撑特性 | `SupportFeature/` | 参数管理、统计、报警、日志、用户 |
| 主框架 / 主界面 | `Main/`、`Infrastructure/` | 启动、机器状态机、权限、动作节点调度 |

**一句话概括运行模型**：软件启动后创建若干**常驻工作线程**（每个子系统一个），线程内是一个 `while (Signal.WaitStart())` 循环，循环体从一条**扁平的动作节点（ActionNode）链**上顺序取节点执行；节点内部通过字符串名字向 `HardwareRepositoryService` 索取硬件对象并驱动它。停机、暂停、急停全部通过一个**全局枚举** `MachineStateModel.MachineState` 生效（详见 §5.4，这是本项目最需要先搞懂的一处设计）。

## 5. 整机工作流程

### 5.1 一个芯片的完整生命周期

```
① 上料：料匣进机 → Mapping 扫描确定基板/芯片位置   TransportUnitSystem/
② 拾取：晶圆台移动到目标 Die → 顶针顶起 → 固晶头下降吸取
③ 点胶：基板到点胶位 → 时间-压力式出胶
④ 对位：上视相机 PR 识别 Die，下视/BOND 相机识别基板固晶位
        → 计算偏差 → 坐标变换 + 二维补偿
⑤ 贴装：Z 轴下降到接触 → 力控加压 → 固化 → 抬起
⑥ 检测：BOND 相机复检（可选）
⑦ 循环：下一个 Die
```

### 5.2 动作编排：本项目的核心设计（**必须先理解**）

整机不写「流程代码」，而是维护一条**扁平的动作节点链表**：

- 每个 `ActionNode` 只暴露 `DoWork()` / `IsDoWork()` / `IsAlarm()`（基类 `Infrastructure/Models/CommonModels/ActionNode.cs:14`）。
- 控制器 `S2ActionNodeController` 用**一个游标**顺序推进：扫描列表，取**第一个 `Finished == false`** 的节点执行（`Main/Machine/Process/S2ActionNodeController.cs`，`标机` 版本 1,630 行）。
- 支持**回退重做**：`SetActionNodeReWork` 把游标拨回，实现返工/重试。

**含义**：想改流程，不是改某个 `if`，而是**改节点列表的组成或顺序**。不理解这一点会在源码里迷路。

### 5.4 停机语义：本项目的"停止"到底怎么工作的（🔴 必读）

**本项目不用 `CancellationToken`，也没有 `while (!IsStop())` 这种写法。** 真正的机制是：

```csharp
// AKRS.Galaxy2.Machine/Models/Signal.cs:202-229   ← 有源码，可直接读
public static bool WaitStart()
{
    if (MachineStateModel.GetInstance().MachineState == MachineStateEnum.Stop)
        return false;                                    // ② 停止 → 退出循环

    while (MachineStateModel.GetInstance().MachineState == MachineStateEnum.Pause)
    {
        if (MachineStateModel.GetInstance().MachineState == MachineStateEnum.Stop)
            return false;
        Thread.Sleep(20);                                // ③ 暂停 → 20ms 空转等待
    }
    return true;                                         // ① 运行 → 继续
}
```

各工作线程的外层循环统一长这样（`BondTask.cs:109`、`DispenseWorkTask.cs:69`、`SlideFluxerTask.cs:97` 等）：

```csharp
while (Signal.WaitStart()) { ...一次生产循环... }
```

**由此推出三条必须牢记的结论**：

1. **停止是靠"外部改全局枚举 + 线程在循环头轮询"实现的**，不是靠协作式取消。
2. 线程创建方式为 `Task.Factory.StartNew(..., TaskCreationOptions.LongRunning, TaskScheduler.Default)`（`BondTask.cs:365`、`SlideFluxerTask.cs:238`），**既不是 `Thread` 也不是 `Timer`**，且**没有任何取消令牌**。
3. ⚠️ **"停止"只对走到循环头的线程有效**。如果线程正卡在某个硬件等待、弹窗或自身的内层循环里，它会**继续跑下去**。这正是 §8.1 那批缺陷的成因，也是 `Machine.Operate.cs:398` 那句原注释的由来：
   > `// TransportDomain.GetInstance().StartTask(); 流道的Task线程不知道怎么结束`

**暂停（Pause）的副作用**：`Thread.Sleep(20)` 是空转轮询，暂停期间该线程会持续占用一个 CPU 核的一部分（20ms 周期的唤醒）。多个子系统同时暂停时是可观测的负载。

#### 暂停、继续、普通停止与急停的区别

| 入口 | 软件实际执行的处理 | 如何理解完成状态 |
|---|---|---|
| `Pause()` | 将机台状态设置为 `Pause`。任务到达 `Signal.WaitStart()` 后在方法内等待 | 暂停不会因为进入 Pause 就直接返回 false；当前正在执行的硬件等待或节点不会因此统一中断 |
| `Continue()` | 未配置安全门时设置 `Working`；配置安全门时先检查门已关闭，通过后恢复首轮点胶标志并设置 `Working` | 恢复工作状态不等于重新创建已退出的任务 |
| `Stop()` | 设置 `Stop`，清除弹窗、更新报警状态、退出单步、复位固晶需料信号；在线模式关闭要料输出，再关闭顶针真空并清零焊后检测计数 | 按调用顺序清理，前面的异常可能中断后续处理；没有统一等待所有任务结束 |
| `EmergencyStop()` | 先对各轴调用 `StopMove(false, true)`，再调用普通 `Stop()`，随后调用各子系统的任务中止入口 | 停轴、软件状态清理和任务退出是不同阶段；中止入口不保证强制结束任务 |

上述入口位于 `Main/Machine/MachineSupport/Machine.Operate.cs`。`Working` 是当前源码中的工作状态名。`20 ms` 是暂停等待时的休眠间隔，**不能用作停机完成时间上限**；任务何时退出取决于它何时再次检查停止状态，以及当时所处的硬件等待、弹窗和内部循环。

### 8.7 🔑 权限与审计模型（**含其重要局限**）

权限机制的实现是 `MethodAopAttribute`（`Infrastructure/AOP/Module/MethodAopAttribute.cs`），靠 Fody 编译期织入到标了该特性的方法上。

**判定逻辑**（`OnEntry`，`:28-92`）：

```csharp
if (arg.Arguments.Length != 2) return;          // :30  ← 参数个数不是 2 就完全不校验！

if (arg.Arguments[1] is ItemClickEventArgs e
    && e.Item is BarButtonItem barButtonItem)   // :36-37 ← 只有 DevExpress BarButton 受检
{
    RoleEnum role = barButtonItem.Tag == null
        ? RoleEnum.Engineer
        : (RoleEnum)(int)barButtonItem.Tag;      // :39  所需角色来自 WinForms 设计器的 Tag
    RoleEnum currentRole = (RoleEnum)Machine.GetInstance().CurrentRoleLevel;  // :41
    if (role.CompareTo(currentRole) < 0
        && MachineSoftwareConfiguration.GetInstance().IsPermissionOpen)       // :44
    {
        AKRSMessageBoxExt.ShowWarn("权限不足，无法执行!...");
        arg.FlowBehavior = FlowBehavior.Return;   // :52  拒绝执行
    }
    StatisticsService.SaveEntity($"点击了主界面按钮：{barButtonItem.Caption}", ...);
}
else if (FocusedNodeChangedEventArgs) { /* 只记日志 */ }   // :60
else if (ImageListBoxControl)         { /* 只记日志 */ }   // :69
else if (SimpleButton)                { /* 只记日志 */ }   // :84
```

**角色模型**：`RoleEnum { Admin = 1, Engineer = 2, Operator = 3 }`（`Infrastructure/Models/Enums/CommonEnum.cs:50-69`）。
**数字越小权限越高**，故 `role.CompareTo(currentRole) < 0` 意为"所需角色权限高于当前用户" → 拒绝。**方向是正确的。**

**必须知道的四点局限**：

1. **只有 DevExpress `BarButtonItem` 的点击被真正鉴权**。`SimpleButton`（普通按钮）、TreeList 节点切换、`ImageListBoxControl` 选择**只写审计日志，不拦权限**。任何挂在普通按钮上的危险操作实际上**没有权限保护**。
2. **参数个数必须恰好为 2** 才进入判定（`:30`）。事件处理器签名不满足时**完全不校验**（静默放行）。
3. **所需角色来自 WinForms 设计器的 `Tag` 属性**，为 `null` 时默认 `Engineer`。改权限要改 `.Designer.cs` 里的 `Tag`，**不是改代码逻辑**。
4. **总开关 `IsPermissionOpen` 默认 `true`**（`Main/Machine/MachineSupport/MachineSoftwareConfiguration.cs:115`），可在参数界面关掉——关掉后全机无鉴权。

**审计侧**：所有上述分支都会调 `StatisticsService.SaveEntity(...)` 落库，记录"谁点了什么"。`OnException`（`:106`）记录"界面操作异常发生"。**审计覆盖面比鉴权覆盖面大**，这是排查操作历史时的有用性质。

**已知的无门禁入口**：`CalibSystem` 的 `FrmStartup`（「设备功能 → 设备自动标定 → 自动标定 → 测试辅助功能」，入口 `UcMainSystem.designer.cs:918-919` → `UcMainSystem.cs:1403`）**无任何权限门禁**，仅受设备状态控制（`UcMainSystem.UIState.cs:203`）；它是 `FrmTestAccuary`（2,635 行硬件调试大杂烩，**含 §8.1 的两处死循环**）的唯一活入口。相比之下，「实验」页 `ribbonPageGroup9` 至少有硬编码密码 `"123456"`（`UcMainSystem.cs:2147`）。

### 第一周（建立认知，不改代码）

1. 读本篇 + `03` + `05`，建立"分层 + 动作节点 + 停机语义"三个心智模型。

4. 用 `git`/文件对比确认你手上代码与**实际装机运行的版本**是否一致（见下条）。

### 动手前的三条红线

1. 🔴 **不要重命名程序集或命名空间**。JSON 参数与坐标数据里内嵌了程序集限定名（`$type`），改名会让历史数据全部反序列化失败（§7.2）。
2. 🔴 **不要删除源码树内那 82 个 DLL**（尤其 `WaferMapFileParser/` 下的 `FileParser1..94`）。它们**不在 `.csproj` 里**，看起来像冗余文件，但晶圆图解析按序号动态加载它们，删除会导致某些晶圆图打不开（§8.8）。
3. 🔴 **改流程不要改 `if`，改动作节点列表**。先读 `05` 与 `S2ActionNodeController.cs`（§5.2）。
