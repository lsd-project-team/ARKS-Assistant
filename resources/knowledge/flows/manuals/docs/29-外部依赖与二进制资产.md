# 外部依赖与二进制资产（`AKRS.ZX2200/libs/`、`packages/`、`bin/`）

> 本篇回答：**这台机器上跑的东西，有多少是我们有源码的、多少是黑盒、多少是过期残留？**
> 本篇所有结论均来自对 `E:\项目\ZX2200标机\trunk` 的实际检查（`ls` / `grep` / `csproj` 解析 / DLL 内嵌 GUID 提取），关键处标注 `文件:行号`。

---

## 1. 为什么这一篇必须单独写

这个解决方案有一个**极不寻常**的结构：

| 事实 | 数值 | 含义 |
|---|---|---|
| 仓库里的工程（`.csproj`） | **16 个** | 有源码、可改；但主程序只引用了其中 **10 个**，且有 1 个已丢失（§4） |
| `AKRS.ZX2200/libs/` 顶层 DLL | **108 个**（其中 `AKRS.*` 仅 34 个） | 多为无源码；但**平台层并非全黑盒**——11 个 `AKRS.Galaxy2.*` 工程有源码，见 §2.1.1 |
| `libs/` 全树 DLL | **406 个**（含 `HikVision/` 187 个） | 无源码、不可改 |
| `libs/` 总体积 | **256 MB** | 其中绝大部分是第三方视觉平台 |
| **源码树内挂载的 DLL**（不在 `libs/`） | **82 个 DLL / 27.7 MB**（+1 个 `.log`），见 §2.5 | 极易被忽略，**csproj 零登记** |
| 主程序源码规模 | 1035 个文件 / 304,163 行 | 相对上述二进制只是冰山一角 |

> **注意**：本节所有"个数"均已逐项核对。先前的口径若称"`libs/` 有 108 个 `AKRS.Galaxy2.*`"是**错的**——108 是 `libs/` 顶层的 **DLL 总数**，其中 `AKRS.Galaxy2.*` 只有 **23 个**，而这 23 个里又有 **3 个仓库内有源码**。这个数字很容易被误传，接手时请以本节为准。

也就是说，**这台设备相当一部分功能不在你能改的源码里**（但**不是全部**——运动控制、力控、IO、测高、配方、用户管理、统计这几块才是真正的闭源部分）。新接手时最容易犯的错误是：在源码里找不到某功能，于是反复搜索；或者更糟——**误把某个过期 DLL 当成权威实现**，改了源码却发现运行行为没变。

本篇给出四张关键地图：**① 哪些平台代码有源码 / 哪些是真黑盒（§2.1.1） ② 哪些 DLL 是过期残留（附 GUID 实证） ③ 构建这台机器需要哪些仓库外的东西 ④ 有哪些一上手就会踩的坑（§10）**。

### 2.2 `.pdb` 文件——黑盒调试的唯一出路

`libs/` 内有 **30 个 `.pdb`**（`AKRS.Galaxy2.AlgebraGeometry.pdb`、`AKRS.Galaxy2.Drive.pdb` 等）。这意味着：

> 虽然平台层没有源码，但 **Visual Studio 可以在这些 DLL 上单步调试并显示行号**（即使没有源码，`pdb` 也能给出调用栈的方法名与行号）。

**这是排查平台层问题的关键手段**。建议做法：VS → 工具 → 选项 → 调试 → 常规 → 取消"仅我的代码"；符号路径指向 `libs/`；在调用栈窗口即可看到平台层内部的方法名。栈帧里出现 `[外部代码]` 时右键 → "显示外部代码"，能拿到准确的方法名，配合反编译工具（ILSpy / dnSpy / dotPeek）即可读实现。

**注意**：`pdb` 只有 30 个，而 DLL 有 108 个——**大部分平台 DLL 没有符号**。有符号的这批恰好是最核心的（Drive / IOControl / Machine / MeasureHeight / Force 等）。

### 2.3 20 个 `*.dll.config` 是无效残留

`libs/AKRS.Galaxy2.Force.dll.config`、`AKRS.Galaxy2.Drive.dll.config` 等 20 个文件，内容形如：

```xml
<configuration>
  <runtime>
    <assemblyBinding xmlns="urn:schemas-microsoft-com:asm.v1">
      <dependentAssembly>
        <assemblyIdentity name="System.Buffers" publicKeyToken="cc7b13ffcd2ddd51" culture="neutral" />
        <bindingRedirect oldVersion="0.0.0.0-4.0.3.0" newVersion="4.0.3.0" />
      </dependentAssembly>
      ...
```

这是这些 DLL 在**作为独立可执行程序编译时**各自的 `app.config` 产物。当它们被当作**库**加载时，**.NET 只读取宿主程序的 `.config`，不读取库的 `.config`** —— 所以这 20 个文件在运行时**完全不起作用**。

真正生效的绑定重定向在 **`bin/Debug/AKRS.ZX2200.exe.config`**。**改绑定重定向要改这一个文件。**

### 2.5 🔴 源码树内挂载的 DLL——**82 个 DLL（+1 个 `.log`）= 83 个文件 / 27.7 MB**，csproj 零登记

> 口径：`ls` 得 83 个文件 = **82 个 `.dll`** + 1 个 `.log`；DLL 实际字节合计 **27.7 MB**（`du -sh` 因块对齐报 29M）。下文的"这 82 个 DLL"与标题的"83 个文件"指的是同一批东西。

**只看 `libs/` 会严重漏掉依赖**。实测发现主程序**源码树内部**的非标准 DLL **全部集中在同一个目录**：

```
AKRS.ZX2200/WaferSubSystem/WaferMapFileParser/     82 个 DLL + 1 个 .log / 27.7 MB
├── AKRS.WM.FileParser.dll            ← 基准版
├── AKRS.WM.FileParser1.dll  …  74.dll ← 版本化解析器（共 74 个）
├── AKRS.WM.FileParser93.dll          ← 编号跳跃（75–92 缺失）
├── AKRS.WM.FileParser94.dll
├── AKRS.PDFConsumer.dll
├── Spire.Pdf.dll     (17.6 MB)       ← 占该目录 64%
├── Spire.XLS.dll      (9.2 MB)       ← 与上者合计 26.8 MB
├── Spire.Common.dll
├── Spire.License.dll
└── （1 个 .log 日志文件）
```

**为什么必须单独记一笔**：

| 检查 | 结果 |
|---|---|
| `AKRS.ZX2200.csproj` 中对 `Spire*` 的 `<Reference>` | **0 条** |
| 对 `AKRS.PDFConsumer` 的引用 | **0 条** |
| 对目录 `WaferMapFileParser` 的 `<Content>`/`<None>` 登记 | **0 条** |
| 对 `AKRS.WM.FileParser` 的引用 | 1 条（仅基准版） |

也就是说：**这 82 个 DLL 既不被编译期引用、也不随构建拷贝**——它们是在**运行时按需加载**的。配合"版本化命名 + 编号 1…74/93/94"的形态，可以判断这是一个**按晶圆图文件格式版本选择解析器的机制**：程序根据 Map 文件里声明的格式版本，在运行时加载 `AKRS.WM.FileParser<N>.dll` 中对应那一个（编号缺口 75–92 说明这些版本要么从未存在、要么已被删除）。

> 姊妹项目 `10-晶圆系统数据模型.md` 独立发现了同一机制（"逐版本反射试探"），两处结论可互相印证。

**运维影响**：

1. **发布清单必须显式包含这 83 个文件**，否则晶圆图解析会在运行时报错——而且因为是运行时加载，**编译期不会有任何提示**。
2. **编号缺口（75–92）是风险**：若现场遇到需要这些版本的 Map 文件，程序会找不到对应 DLL。接手时应向原团队索取 75–92 的说明。
3. `Spire.Pdf.dll`（17.6 MB）+ `Spire.XLS.dll`（9.2 MB）合计 **26.8 MB**，占了该目录 27.7 MB 的 **97%**——它们只被 `AKRS.WM.FileParser` 用来读 Excel/PDF 格式的晶圆图。
4. **Spire 是商业库**（E-iceblue）。`Spire.License.dll` 的存在说明有授权管理机制。**Spire 免费版有水印与页数/行数限制，商用需购买授权** —— 请与采购确认，见 §10。
5. `AKRS.Galaxy.SoftKey/AKRS.Galaxy.SoftKey/package/USL3.dll` 是另一处"源码树内挂载 DLL"，属授权工程（见 §7）。

## 3. ⚠️ 过期残留——本篇最重要的一节

**这是新接手最容易踩的坑**，且本项目的情况比一般项目严重。检测方法：**把 DLL 内嵌的 `GuidAttribute` 与仓库内 `.csproj` 的 `ProjectGuid` 做比对**——若一致，说明这个 DLL 就是那个工程的**旧编译产物**。

### 3.2 🔴 实锤缺陷：主程序链接的是旧版 `AKRS.DispensingPattern.dll`

因为两者**程序集名不同**（`AKRS.Galaxy2.Dispense` vs `AKRS.DispensingPattern`），编译器**不会报错**——但运行时**同一份源码的新旧两个版本被同时加载**，`EpoxyPattern` 相关的类型在进程里存在**重复定义**。

**后果**：
- 改了 `AKRS.Galaxy2.Dispense` 源码 → 行为不生效（因为实际实例化的是旧 DLL 里的类型）
- 跨这两套类型做强制转换 → 可能抛 `InvalidCastException`
- 排查此类问题的难度极高，因为**编译器不会给任何提示**

**处置建议**：确认 `AKRS.DispensingPattern.dll` / `AKRS.EpoxyPatternEditor.dll` 确实无人使用后移除引用与文件；若确有使用，必须统一到源码工程。**修改前先在 `bin/Debug` 上做全量回归**。

### 3.3 同类陷阱的通用检测法（值得记下来）

## 6. 视觉与推理栈

本机的视觉能力**名义上有四个来源，实际在用的只有两家**（HALCON + VisionMaster），另两家的二进制虽在 `libs/` 却零引用。改影像相关功能前**必须确认走的是哪一路**：

|---|---|---|---|
| **MVTec HALCON 17.12** | `HalconDotNet`、`HObject`、`HOperatorSet` | **6 个文件** | 商用授权，`halcondotnet.dll`（引用声明 `Version=17.12.0.0`） |
| **海康 VisionMaster (iMVS)** | `VM.*`、`VMControls.*`、`IMVS*ModuCs` | **22 个文件**（`using VM` 口径；`using VM.` 为 20） | 商用授权，`libs/HikVision/` 整套 **187 DLL** |

| 自研/未知 | `ImageAlignmentDll.dll` | ⚠️ **0 个文件**，csproj 亦无 `<Reference>` | 只有 DLL，**未被使用** |

> ⚠️ **只看 `libs/` 会高估视觉栈**：上表后两行（OpenCV、`ImageAlignmentDll`）虽然文件都在，但**源码里一处都没用**。

### 8.2 AOP：编译期织入 + 运行时补丁 双轨

**编译期**：`FodyWeavers.xml`（本仓库**只有 2 个**：`AKRS.ZX2200/` 和 `AKRS.Galaxy2.PR/`）

```xml
<Weavers>
  <PropertyChanged />        <!-- PropertyChanged.Fody 4.1.0 -->
  <MethodBoundaryAspect />   <!-- MethodBoundaryAspect.Fody 2.0.145 -->
</Weavers>
```

- `PropertyChanged` → **所有实现了 `INotifyPropertyChanged` 的类的属性 setter 被编译期改写**。这解释了大量 `UcParameter*` 类为何"看不到 `OnPropertyChanged` 调用却能刷新界面"。
- `MethodBoundaryAspect` → 方法出入口被织入。`MethodAopAttribute`（方法级鉴权切面）依赖它。

> **⚠️ 反编译所见 ≠ 源码。** 因为 Fody 在编译后改写 IL，用 ILSpy 打开 `AKRS.ZX2200.dll` 会看到源码中并不存在的 `PropertyChanged` 触发代码。**不要以反编译结果为准，要看源码。**

**另外还有 `libs/PostSharp.dll`** —— 第二套 AOP 框架。源码中没有 `<PostSharp>` 特性使用（需在源码中确认），很可能与 `PostSharp` 的 `<Reference>` 是遗留。两套 AOP 框架共存而只启用其中一套，属于清理对象。

**运行时**：`Program.cs:242-247` 使用 **Harmony**（`packages/Lib.Harmony.2.3.6`，运行时为 `bin/Debug/0Harmony.dll`）对 `System.Windows.Forms.Application` 的**私有嵌套类 `MarshalingControl` 的构造函数**打补丁。

这是一个**高风险但已知有效**的技巧：`MarshalingControl` 是 WinForms 用于跨线程封送的内部控件，其构造函数在框架内部被调用；补丁它等于**在框架层插入钩子**。风险：

- 依赖 .NET Framework 内部实现细节 —— **升级 .NET 版本会导致补丁静默失效**（Harmony 找不到目标方法时若未开启严格模式，可能不抛异常）
- 无源码、无文档、无测试覆盖

**新接手务必先读 `Program.cs:230-260` 附近**，搞清楚这个补丁到底做什么——它可能是某个诡异行为（例如消息泵/异常处理/DPI）的唯一成因。

### 8.3 平台目标：Debug=x64，Release=**AnyCPU**（危险）

主程序 `.csproj` 中：

| 配置 | `PlatformTarget` |
|---|---|
| Debug | `x64` |
| **Release** | **`AnyCPU`** |

而主程序引用了大量**仅 x64** 的程序集（`processorArchitecture=AMD64`）：全部 `AKRS.Galaxy2.*` 平台 DLL、ETEL 的 `dex40net`/`dsa40net` 等、`AKRS.Galaxy2.Infrastructure`、`AKRS.Galaxy2.Force` 等。

**结论**：**Release 配置极可能无法运行**（`BadImageFormatException`：试图在 32 位进程中加载 64 位程序集）。若必须出 Release 版，**先把 `PlatformTarget` 改为 x64**，并逐项核对所有平台的 `PlatformTarget` 一致性。

`.sln` 的配置映射表还显示：多数附属工程把 `Debug|x64` / `Release|x64` 映射到 `Debug|Any CPU` / `Release|Any CPU`（例如 `{EB3C2BCE-…}`=Machine、`{2B9696AB-…}`）。**解决方案级配置与工程级配置不一致**，是这类问题的温床。

```xml
<package id="System.Threading.Tasks.Dataflow" version="6.0.0" ... />
```

**`packages.config` 要 Fody 6.6.4，而本地缓存里只有 6.0.5** —— 存在版本不一致。首次在新机器上构建时**必须能联网执行 NuGet 还原**；离线环境会因缺包而失败。

**更重要的观察**：主程序 `csproj` 的 `<Reference>` 有 **140+ 条**，而 NuGet 包只有 **4 个**（Fody 系列）+ Harmony。也就是说：

> **除了 Fody/PropertyChanged/MethodBoundaryAspect/Dataflow 这四个，其余全部第三方库都是"裸 DLL 引用"**（`<HintPath>libs\xxx.dll</HintPath>`），不走 NuGet。

**维护影响**：
- 升级任何一个第三方库 = **手工替换 `libs/` 下的 DLL**，没有版本约束、没有依赖解析、没有传递依赖检查
- 这类手工替换极易踩到**版本冲突**（例如 `Newtonsoft.Json` 被多个组件以不同版本要求）
- **`bin/Debug/AKRS.ZX2200.exe.config` 的绑定重定向是唯一的安全网** —— 改库版本后务必核对这个文件

### 8.5 安装包工程

`SetupZX2200/SetupZX2200.vdproj` 是 **Visual Studio Installer Project**（`.vdproj`）格式。**该工程类型在 VS2022 及以后版本需要单独安装扩展**（"Microsoft Visual Studio Installer Projects"），且微软已多年未更新。

**新接手提醒**：打开这个安装工程可能报"不支持的工程类型"。若接收方无法安装该扩展，需要考虑迁移到 WiX / Inno Setup 等现代方案。

## 9. 运行时目录结构（`bin/Debug/`）

### 9.1 输出目录的位置**不是**默认位置

| 检查 | 结果 |
|---|---|
| 工程声明的 `OutputPath` | `bin\Debug\`（相对 csproj，应为 `AKRS.ZX2200/bin/Debug/`） |
| `AKRS.ZX2200/bin/Debug/` 实际内容 | **空目录**（仅有空壳） |
| **实际运行目录** | **`<仓库根>/bin/Debug/`** —— 296 个文件，含 `AKRS.ZX2200.exe`（16.9 MB） |

说明输出路径被解决方案级配置或构建脚本重定向到了仓库根的 `bin/Debug/`。`PostBuildEvent` 在 `csproj` 中**未找到**，故重定向来自 `.sln` 配置。

> **排障即在此**：日志、配置、模型、崩溃现场都在 **`<仓库根>/bin/Debug/`**，不在 `AKRS.ZX2200/bin/`。找错目录会白费很多时间。

### 9.2 ⏰ 当前构建产物已过期约 13 个月

```
bin/Debug/AKRS.ZX2200.exe    16,970,752 字节   2025-08-24 09:05
bin/Debug/ZX2200Data.db          49,152 字节   2025-08-24 09:20
（今天是 2026-09-20）
```

**`bin/Debug/` 里的可执行文件是 2025 年 8 月的旧构建**。在基于它做任何结论之前，**先在 VS 里重新构建一次**——否则你调试的是别人一年前的代码。

### 9.3 `bin/Debug/Settings/` —— 参数持久化（910 个 JSON）

运行时参数不是存在数据库里，而是**以 JSON 文件形式按类的命名空间路径镜像到目录树**：

```
bin/Debug/Settings/
├── MachineConfig.json                    ← 机器总配置
├── RecipeList.json                       ← 配方清单
├── ZX2200Data.db                         ← SQLite 文件，见 §9.4
├── ControlConfigs/
└── DeviceParams/                         ← 设备参数主体
    ├── AxisCompensateProgram.json
    ├── BondCompensate.json / BondCompensateCalibration.json
    ├── BondDeviceParaPath.json / BondRecipeParaPath.json
    ├── BondPositionRepository.json / BondinsertSettingRepository.json
    ├── BondLevelMeasureFilePath.json
    ├── BondSystem/{Controls,Models,Modules,Services,Tasks}/   ← 镜像源码目录！
    ├── CalibSystem/{Controls,Models,Services}/
    ├── DispenseSystem/{Controls,Models,Modules,Services,Tasks}/
    ├── CalibrationStorageFilePath/  ClosedLoopCalibrationStorageFilePath/
    ├── CarrierPathConfig/  ForceCalibrationDataFilePath/
    └── Configurations/{Advanced,Application,General,Hardware,Secure,Software}/
```

**要点**：
- **共 910 个 JSON**。参数系统规模很大，且**目录结构与源码目录结构一一对应**——先知道类在哪个命名空间，就能预测参数文件在哪。
- 平台层用 **Newtonsoft.Json 的 `$type` 元数据**（含程序集全名）。**改程序集名或命名空间会导致历史参数文件全部无法反序列化**。这是 §3 中"改工程名"的旧产物陷阱之外，第二个改名代价。
- `Configurations/Secure/` 目录名暗示存放敏感配置（口令/密钥），**交付时需确认其中没有明文凭据**。

### 9.4 🔎 存在**第二个**数据库：SQLite `ZX2200Data.db`

主流认知是"本项目用 SQL Server `ZX2200`"。但 `bin/Debug/` 下有：

```
ZX2200Data.db                49 KB (SQLite 格式)
bin/Debug/x64/SQLite.Interop.dll
bin/Debug/x86/SQLite.Interop.dll
```

而**主程序源码中对 `ZX2200Data` / `SQLite` 的引用为 0 处**。

**判断**：这个 SQLite 库**不属于主程序**，最可能属于 **Hikvision VisionMaster 平台**（VM 平台用自己的 SQLite 存视觉流程/算子配置，并需要 `SQLite.Interop.dll` 原生库）。`bin/Debug/x64` 与 `x86` 两个版本正好对应"平台可运行于两种位数"。

**结论**：**不要动 `ZX2200Data.db`** —— 它不是你的数据库，删了会丢视觉配置。主程序的数据库是 SQL Server 上的 `ZX2200`。
