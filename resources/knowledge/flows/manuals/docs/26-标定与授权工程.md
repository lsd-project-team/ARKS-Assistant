# 标定与授权工程（`AKRS.Calibration` / `AKRS.Galaxy.SoftKey`）

> 两个各自独立、都被主程序 `AKRS.ZX2200` 以 `ProjectReference` 挂进解决方案的外部工程：一个是被主程序彻底弃用的 VisionMaster 标定小工具，一个是启动链最前端真正在跑的加密锁校验工程。
> 代码规模：18 个文件 / 3,776 行（不含 `*.Designer.cs` 为 11 个文件 / 3,004 行）

本文件只写这两个工程**自身**。主程序内的标定体系（`AKRS.ZX2200/CalibSystem/`，65 个文件 / 28,635 行）见 `13-整机标定.md`、`14-标定系统界面与测试.md`；二进制资产与授权文件的清单见 `29-外部依赖与二进制资产.md`；启动链上下文见 `01-启动流程与主界面.md`。

> **关于授权（SoftKey）部分的阅读约定**：本文件只做技术描述——公开接口签名、调用者、调用时机、校验失败时的分支与提示、涉及的外部依赖与运行时组件。不含任何绕过/破解/伪造/禁用授权的思路、步骤或代码片段，也不对校验实现的强度做评估。

## 1. 模块定位

两个工程没有业务关系，只是恰好都挂在同一个解决方案里。

### 1.1 `AKRS.Calibration` —— 一个被"吞掉"但未被使用的标定工具

- 它是 `OutputType=Library`（`AKRS.Calibration.csproj:8`）但内部仍保留 `Program.Main()` + `Application.Run(new FormCalib())` 的完整可执行程序结构（`Program.cs:17`、`Program.cs:21`）。**这套入口在库形态下永远不会被调用**。
- 它的历史形态是一份被改名为 `.txt` 的旧工程文件 `AKRS.Calibration.txt`：那份里 `OutputType=WinExe`、`Compile Include="Calib.cs"` / `"Form1.cs"`（现名 `Correction.cs` / `FormCalib.cs`）、DevExpress 版本为 `v23.1`（现行 `.csproj` 为 `v21.2`）、引用 `LightControlCs`。即：**它曾是独立标定小工具（日志文件固定写在 `./log/LocateDemoCs.log`，见 `FormCalib.cs:267`，可见原始 Demo 名为 LocateDemoCs），后被改造成库塞进主程序，但主程序一行都没用**。
- 主程序侧只有一条 `<ProjectReference>`（`AKRS.ZX2200.csproj:4050`），**没有任何 `using AKRS.Calibration;`，也没有对 `FormCalib` / `Correction` / `LocateTypeEnum` / `MainViewControl` / `RenderControl` 的任何引用**（全仓 `.cs` 检索为空）。用元数据核实：已编译的 `bin/Debug/AKRS.ZX2200.exe` 的 67 条 `AssemblyRef` 里**没有 `AKRS.Calibration`**（C# 编译器不会为"引用了但没用到"的程序集生成 `AssemblyRef`）。也就是说这条 `ProjectReference` 的唯一效果是让 `AKRS.Calibration.dll` 被产出到 `..\AKRS.ZX2200\bin\Debug\`（`AKRS.Calibration.csproj:20` 显式指定）并被打包程序带进安装包（`SetupZX2200/SetupZX2200.vdproj:15410`、`:21389`），运行期从不加载。
- 它与主程序 `CalibSystem/` 的关系：**两条互不相通的标定实现路线**。
  - 主程序路线：`CalibService.NPointTrans` + `MachineCoordinateSystem`/`.iwcal` + ETEL/固高映射表（见 `13-整机标定.md`），做的是"像素↔轴坐标"的坐标系标定，**纯 Halcon**。
  - 本工程路线：把标定做成海康 **VisionMaster** 的 `.sol` / `.prc` 方案，由 `FormCalib` / `Correction` 调 `VmSolution` / `VmProcedure`。`CalibrateTask.cs:550`、`CalibrateTask.cs:852` 各留有一行**被注释掉的** `Correction.GetInstance().UpLookCamCalib(...)` / `WaferCamCalib(...)`，而且该文件连 `using AKRS.Calibration;` 都没有——**当年是"想用、试用过、然后放弃并注释掉"的状态**，之后主程序自己用 Halcon 重写了一遍。
  - 因此：本工程不是 `CalibSystem/` 的上游或下游，改它不会影响整机标定；反之亦然。

### 1.2 `AKRS.Galaxy.SoftKey` —— 启动链上的加密锁校验

- 它是 `OutputType=Exe`（`AKRS.Galaxy.SoftKey.csproj:8`），既是一个可独立运行的小程序（`Program.cs:12` 双击 `AKRS.Galaxy.SoftKey.exe` 即做一次校验并弹授权窗体，安装包确实带了这个 exe：`SetupZX2200.vdproj:20447`），**又是一个被主程序当类库引用的程序集**（`AKRS.ZX2200.csproj:4054`）。
- 主程序在启动链的最前端调用它的公开静态方法：`AKRS.ZX2200/Program.cs:141` 的 `SoftkeyManager.CheckYtSoftKey()`（`Program.cs:12` 有 `using AKRS.Galaxy.SoftKey;`）。校验不通过则 `mutex.ReleaseMutex(); return;`（`Program.cs:143-144`），主进程直接结束。
- 部署形态：`AKRS.Galaxy.SoftKey.exe` 作为程序集被主程序加载（已核实 `bin/Debug/AKRS.ZX2200.exe` 的 `AssemblyRef` 中含 `AKRS.Galaxy.SoftKey`）。同一个文件夹里另有一份**旧产物** `libs/AKRS.Galaxy2.SoftKey.dll`（`AssemblyName=AKRS.Galaxy2.SoftKey`、`ProjectGuid` 与本工程相同），主程序既不 `Reference` 也不部署它，是上一代实现留下的死文件（`29-外部依赖与二进制资产.md` §3.1 亦有记载）。

## 5. 关键实现细节

### 5.1 加密锁的"进程 + 共享内存"通信模型

- 通信对象是一个**外部 exe**：常量 `SOFTKEY_PROCESS_NAME = "AuthenticatorBG_x86"`（`SoftkeyManager.cs:188`），启动参数是 `"<Guid> 6000"`——第一个参数是本进程生成的 MMF（内存映射文件）名 `szMmfId`（`SoftkeyManager.cs:252`），第二个是更新间隔 `TIME_DELAY`（`SoftkeyManager.cs:190`）。
- 每次 `InitSoftKey()` 都会先 `Release()` 掉旧连接（`SoftkeyManager.cs:69`），`Release()` 会 `threadReadkey.Abort(); threadReadkey.Join();` 再 `Kill()` 掉进程（`SoftkeyManager.cs:339-348`）。`CreateSoftkeyProcess()` 还会先扫一遍同名进程并 `Kill`（`:237-248`）——**不支持多实例**。
- 读取侧调 `Authenticator_BGx86.ReadBGx86Result(szMmfId)`（`SoftkeyManager.cs:290`），返回 `ST_AUTH_RESULT`（字段 `m_iUserId` / `m_lLimitTime` / `m_lLastCheckTime`）。该类型在 `libs/Authenticator.dll` 的 `Authenticator` 命名空间里；同 DLL 内还有一组 `HidSoftKey.SoftKey2K` P/Invoke 封装（HID 加密锁原生读写），本工程未直接使用。
- 状态更新只在后台线程写、UI 线程读（`softkeyConn.UserId` / `.LimitTime` / `.ErrorMessage`），**无 `volatile`/锁保护**，属"写一次读多次"的实际用法，但 `errorMessage` 与 `firstRead` 的可见性没有内存屏障保证。
- `CreateSoftkeyProcess()` 的 `while (firstRead) { ... Thread.Sleep(10); }`（`SoftkeyManager.cs:263-270`）跑在**调用线程**上（也就是主程序启动线程），靠"后台线程一定会在成功或报错后离开循环"来保证不会死等。

### 5.2 `Galaxy.SoftKey.SoftkeyManager` 这个名字其实是本类自己

`SoftkeyManager.cs:22`、`:30`、`:37` 写作 `Galaxy.SoftKey.SoftkeyManager.InitSoftKey()` 等，看起来像在调外部平台类型，实际上 **C# 名称解析把 `Galaxy` 逐层向外找到 `AKRS.Galaxy`，再拼出 `AKRS.Galaxy.SoftKey`——正是本类型自身的命名空间**。因此这三行是**对本类方法的自调用**。证据：

- 用 `csc` 单独编译本工程 6 个源文件（引用 `Authenticator.dll`/`log4net`/`SunnyUI`/`USL3.dll`）**零错误通过**；
- 逐文件扫描仓库内所有 `.dll`/`.exe` 的元数据字符串，**不存在** `Galaxy.SoftKey` 这一独立命名空间；
- 已编译的 `bin/Debug/AKRS.Galaxy.SoftKey.exe` 中 `CheckYtSoftKey` 的 IL 调用目标全部落在 `AKRS.Galaxy.SoftKey.SoftkeyManager` 自身。

接手时不要把它当成"平台 DLL 委托"，这只是一个多余的限定前缀。

### 5.3 `AKRS.Calibration` 的计算模型

- **变换靠 VisionMaster**：所有"图像坐标 → 机械坐标"都通过 `VmProcedure.Load(<.prc 文件>)` → `SetInputFloat` → `Run()` → `GetOutputFloat` 完成（`Correction.cs:1082-1096`、`:1126-1139`、`:1169-1179`、`:1210-1226`），**每个点都重新 Load + Dispose 一次流程**。4 个转换函数各对自己那一个 `.prc` 路径硬编码。
- **几何计算靠 Halcon**：仿射矩阵由 `HOperatorSet.VectorAngleToRigid`（`Correction.cs:752`、`:858`）生成，点映射用 `AffineTransPoint2d`（`Correction.cs:999`）。
- `FormCalib` 的 4 个标定方法走的是另一条路：整份 `.sol` 方案 + 具名流程（`"1下相机12点"`、`"3上相机12点"`、`"4点胶9点标定"`、`"5晶圆相机9点"`），`SetInputFloat` 灌入点集后取 `CameraScale`/`TransX`/`TransY`（`FormCalib.cs:571-586`）。
- 三处循环判据写法为 `if (isSuccess == procedureResult.GetOutputInt("isSuccess").pIntVal[0]) return false;`，而 `isSuccess` 局部变量恒为 0（`Correction.cs:1289`、`FormCalib.cs:551` 等）——实际语义是"方案输出 `isSuccess == 0` 即视为失败"。
- 唯一被填实的状态是 4 个 `static VmProcedure` 字段，`Init()`（`Correction.cs:76`）里的预加载逻辑**从未被调用**（构造里注释掉了 `:68`），实际靠各转换函数自己 Load/Dispose 覆盖，所以那些 `if (xxx == null)` 判断形同虚设。

### 5.4 窗体与控件

- `FormCalib` 标题仍是设计器默认的 `"Form1"`（`FormCalib.Designer.cs:258`），未本地化；布局为左侧 `renderPanel`（1084 宽）+ 底部 `panelControl1`（341 宽，含 3 个 GroupControl：选/载/存、流程选择、日志 ListView），客户区 1425×770（`FormCalib.Designer.cs:251`）。

- `FormCalib` 用 DevExpress 皮肤，`FormSoftKey` 用 `Sunny.UI.UIForm`（`FormSoftKey.cs:14`）：同一套发布里两种窗体风格（这也是主程序 `bin/Debug` 里带上 3.4 MB `SunnyUI.dll` 的原因）。

## 8. 注意事项与风险

### `AKRS.Calibration`

1. **主程序完全不用它**（§1.1，已用 `AssemblyRef` 核实）。它的存在只增加编译时间、`bin` 体积和安装包体积（`AKRS.Calibration.dll` + `.pdb` + `.dll.config`）。若要清理，删除 `AKRS.ZX2200.csproj:4050-4053` 的 `ProjectReference` 与安装包条目即可；但要注意 `AKRS.Calibration.txt` 表明这份代码是**唯一留存**的 VisionMaster 标定版本，删前先确认不再需要。
2. **所有数据路径都是别人桌面**：`C:\Users\user\Desktop\视觉标定项目\...`（共 17 处，见 §7）。在开发机上 `VmSolution.Load` / `VmProcedure.Load` 抛异常后大多被 `catch (Exception) { return false; }` 或 `catch { MessageBox.Show("...失败") }` 吞掉（`Correction.cs:1100`、`:1142`、`:1184`、`:1231`；`FormCalib.cs:107`），**表现为"标定结果全 0 且不报错"**。接手时第一件事是确认这两个目录是否还存在于某些现场。
3. **`Correction` 与 `FormCalib` 有 4 个逐字重复的方法**（`DripCalib` / `BondCamCalib` / `WaferCamCalib` / `UpLookCamCalib`，`Correction.cs:1287/1349/1412/1477` 与 `FormCalib.cs:549/611/675/741`，共约 650 行）。改动其一必须同步改另一个。
4. **`GetXYAngOffsetByP1P2` 有明确的形参错用**：`Correction.cs:417-418` 把 `CalculateMidpoint` 的第二、四个实参都写成了 `p1AbsBasePoint.X`（base 与 mark 两行同样错法）。
   ```
   (double baseMidX, double baseMidY, double baseAngle) = this.CalculateMidpoint(p1AbsBasePoint.X, p1AbsBasePoint.X, p2AbsBasePoint.X, p2AbsBasePoint.Y);   // :417
   (double markMidX, double markMidY, double markAngle) = this.CalculateMidpoint(p1AbsMarkPoint.X, p1AbsMarkPoint.X, p2AbsMarkPoint.X, p2AbsMarkPoint.Y);   // :418
   ```
   按签名（`x1,y1,x2,y2`，`:264`）推断，第 2 个实参应为 `...Y`。
5. **`GetJointPositionByP1P2P3Affine`（`:522`）里的矩阵永远为空**：它调用的 `CalcuSubMapP1P2P3` 整段被注释（`:527` 引用、`:948-983` 定义体已注释），`homMat2d` 始终是 `new HTuple()`，随后直接 `MapPointTrans`。该方法目前是 `private` 且无调用者，属死代码。
6. **`Form1_Load` 会向面板塞一个 `null`**：`mainViewControl` 字段从未实例化（`FormCalib.cs:81-86` 构造部分被注释），但 OnLoad 里执行 `renderPanel.Controls.Add(this.mainViewControl)`（`FormCalib.cs:505`）、`BtnConfig_Click` 里同样（`FormCalib.cs:198`）。实测 `.NET Framework` 的 `ControlCollection.Add(null)` **不抛异常、静默无效**，所以现象是"参数配置页永远空白、不报错"。
7. **空捕与死代码**：`catch (Exception) { return false; }` 遍布（`Correction.cs:1100/1142/1184/1231`）；`AppendLog` 的 `catch` 直接 `throw new Exception(ex.Message)`（`FormCalib.cs:277`，会丢掉原始堆栈）；死代码包括 `Program.Main`、`Correction.Init()`、`GetAngle`/`GetJointPositionByP1Offset`/`GetJointPositionByP1P2Offset`/`GetJointPositionByP1Location`/`GetJointPositionByP1P2Location`（`Correction.cs:237/435/464/542/569`，均 private 且无调用者）、`GetJointPositionByP1P2Affine`（`:500`）、整段注释掉的 `CalcuSubMapP1P2P3`（`:865-984`、`:641-677`）、`LocateTypeEnum` 两个枚举（全工程无使用）。
8. **`Correction` 每次转换都 `Load`/`Dispose` 一个 `.prc`**（§5.3），单点调用即有文件 IO + 方案解析开销；`GetOffsetWorld` 每次要转 2 个点（`Correction.cs:1255-1269`），`GetXYAngOffsetByP1P2` 一次要转 4 个（`:394-404`）。
9. **`Correction` 的单例是"半个"**：`GetInstance()`（`:54`）走静态字段，但构造函数是 `public`（`:66`），任何地方 `new Correction()` 都会绕过单例（`static` 字段仍会被覆盖写法共享，容易产生竞态）。
10. **`CalcOffset` 的角度没有真正参与上视旋转**：它算出 `rotateAngle = upLookAngle + bondAngle`（`Correction.cs:218`），却把 `CalcUpLookOffset` 的角度实参写死为 0（`:221`），该方法内部才用 `Rotate(...)`（`:144`）。这是刻意还是遗漏，源码里没有注释说明。
11. `AKRS.Calibration.csproj:8` 是 `OutputType=Library`，但 `Program.cs` 保留了 `Main`；若将来把它改回 `WinExe` 并单独运行，会立刻撞上 §2 的路径问题。
12. 工程文件与目录命名不一致：`AKRS.Calibration.txt`（旧 `WinExe`/DevExpress 23.1 工程）、空目录 `Modules/`（`AKRS.Calibration.csproj:219`）、`.resx` 与 `.Designer.cs` 均齐全但 `Controls/MainViewControl.resx` 与 `Controls/RenderControl.resx` 内容完全相同（各 5817 字节）。

### `AKRS.Galaxy.SoftKey`

13. **`SoftkeyConnection.LastTime` 是无限递归属性**：`get { return this.LastTime; }`（`SoftkeyManager.cs:228-231`），一旦被读取必然 `StackOverflowException`。目前全仓无调用者（排在 §4.2 之外），但它是 `public`，没有任何保护。
14. **`Thread.Abort()`**：`Release()`（`SoftkeyManager.cs:343`）用 `threadReadkey.Abort()` + `Join()` 结束读线程。在 .NET Core/.NET 5+ 上 `Abort` 会抛 `PlatformNotSupportedException`（本工程为 `v4.8` 尚可用），且线程可能正卡在 `Authenticator_BGx86.ReadBGx86Result` 里。

20. **`AKRS.Galaxy2.SoftKey.dll` 是死文件**（`libs/`，与 `AKRS.Galaxy.SoftKey.csproj` 同 `ProjectGuid` 的旧构建，含本代已删除的 `SoftKeyInfo`/`KeyPath`），容易让接手者误以为是"外部平台 DLL"。同名 `.dll.config`、`.pdb` 一并存在。
21. **`USL3.dll` 是悬空引用**（§6.3）：`AKRS.Galaxy.SoftKey.csproj:61-63` 引用它、`SoftkeyManager.cs:5` `using` 它，但**没有用到其中任何类型**，产物与安装包都不含它。若删掉引用与那行 `using`，编译结果不变。它自身还引用了本目录不存在的一批程序集（`AKRS.PR`、`AKRS.MessageString` 等），即使想在别处用它也需要补齐依赖。
22. **`CheckYtSoftKey` 的调用时机使启动流程被阻塞**：`Program.cs:141` 的调用发生在 `SplashScreenManager.ShowForm` 之前（`Program.cs:179` 才启动 Splash），而 `CheckYtSoftKey` 内部可能弹 `MessageBox` / 模态窗体（`SoftkeyManager.cs:77`、`:87`、`:114`；`FormSoftKey.ShowDialog`）；并且 `InitSoftKey` 在 `Program.cs:148` 被**重复调用一次**（`CheckYtSoftKey` 内部已调过），会再 `Kill` 一次并重启 `AuthenticatorBG_x86.exe`。这两点都是排障时"启动卡住/闪退"的第一现场。
