# 机器模型与流程调度（`AKRS.ZX2200/Main/Machine` + `AKRS.Galaxy2.Machine` / `AKRS.Galaxy2.MachineSupport`）

> 全机唯一的机器门面 `Machine` 单例，加上「制程 → 动作节点序列」的翻译器 `ProcessDomain` / `S*ActionNodeController`，以及平台层的状态机与线程信号。
> 代码规模：39 个文件 / 9,013 行（不含 `*.Designer.cs`；含 8 个 Designer 文件共 47 个文件 / 10,968 行）

---

## 1. 模块定位

本模块是**整机主控层**，位于业务子系统（`BondSystem` 固晶、`DispenseSystem` 点胶、`TransportSystem` 流道、`WaferSubSystem` 晶圆）之上、主界面（`Main/Controls`）之下，回答三个问题：

1. **整机现在是什么状态**（`MachineStateEnum`：Stop / Pause / Working / Operate / Teaching / Preparing）。
2. **一次自动生产要按什么顺序做哪些动作**（制程 `ProcessDomain` 把「步骤 `SingleProcessStep`」展开为动作节点序列 `List<ActionNodeMessage>`）。
3. **各子系统线程如何互锁**（`SignalPool` 的跨线程信号 + `Signal.WaitStart()` 暂停/停止语义）。

三层结构：

| 层 | 位置 | 职责 |
|---|---|---|
| 平台层 | `AKRS.Galaxy2.Machine`、`AKRS.Galaxy2.MachineSupport`（**仓库内有源码**） | 状态机 `MachineStateModel`、线程信号 `Signal`/`SignalPool`、单步跟踪 `BaseMachine`、路径 `PathConfig`、运行时 `RuntimeProvider` |
| 项目主控层 | `AKRS.ZX2200/Main/Machine`（**本篇主体**） | 机器门面 `Machine`（启动/停止/自检/数据加载）、制程 `ProcessDomain`、动作节点排序 `S1/S2ActionNodeController`、硬件/软件配置 |
| 业务层 | `BondSystem/`、`DispenseSystem/` 等（不在本篇范围） | `BondTask`、`DispenseWorkTask` 消费 `ActionNodeMessage` 序列并真正驱动硬件 |

**上游**：`Main/Controls/MainForm.cs`（`MainForm_Load` 调 `DataLoad` / `StartBackGroundThread`）、`Main/Controls/Ucmain/UcMainSystem.*`（启动/停止/暂停按钮）、`Program.cs`（硬件初始化）。

**下游**：`System2Domain.BondTask`（`BondTask.cs:216` 调 `ActionNodesService.GetNextActionNode()`）、`System1Domain.DispenseWorkTask`（`DispenseWorkTask.cs:119` 调 `S1ActionNodeController.GetNextActionNode()`）、`FlipTask`、各 `ActionNode.DoWork()`。

**与兄弟项目 ZX2200DAF-2 的关键差异（务必按本项目实测理解）**：本项目 `BondTask.DoWork()` 的主循环是 `while (Signal.WaitStart())`（`BondSystem/Tasks/BondTask.cs:109` 外层、`:214` 内层动作循环），**不是** `while (!IsStop())`。`BondTask.cs:450` / `:463` 的 `if (Machine.GetInstance().IsStop() == false)` 只出现在 `SendAway()` 里，用于判断「是不是点了停止、还要不要给流道发允许传送信号」，与主循环无关。点胶侧同理（`DispenseSystem/Tasks/DispenseWorkTask.cs:69` / `:117` / `:172`）。

`MachineStateModel`（`AKRS.Galaxy2.Machine/Models/MachineStateModel.cs:24`）是**自实现的双检锁单例**（`:54-74`），首次访问时从 `<exe目录>/Settings/DeviceParams/MachineStateModelPath.json` 反序列化（路径拼装见 `:39`），`Save()`（`:79`）写回。关键派生属性：`IsOffLineWork`（`:104`）、`IsDryCycle`（`:110`）、`IsCompensateWork`（`:116`）、`IsNormalWork`（`:128`）。

`Machine.SetState()`（`Machine.StateRelated.cs:52`）**状态变化时写一条 `ParameterChangeLogEntity` 到 `StatisticsService.DbEntityBlockingCollection`**（`:58-65`）——即每次启停都会有一条「设备状态」参数变更记录入库，且携带当前登录用户名。`DebugPauseTime` / `DebugModel` / `ContinueDebug`（`Machine.cs:97/103/109`）不在状态机内，而是给 `System2RunTimeProvider` 做单步调试耗时统计用（`System2RunTimeProvider.cs:236-244`）。

### 5.2 `Signal` 的三态语义（本项目并发的核心）

`Signal`（`AKRS.Galaxy2.Machine/Models/Signal.cs:16`）包了一个 `EventWaitHandle`，轮询周期 `recycleTime` 在**单参构造函数里被指定为 100ms**（`Signal.cs:47` 的 `: this(name, 100, …)`）；⚠️ 但**字段本身的初值是 5**（`Signal.cs:41` `private int recycleTime = 5;`）—— 两个数字别混：**凡经构造函数创建的（`SignalPool` 全部如此）都是 100ms；字段初值 5 只在绕过构造函数时才会生效**，实际上不可达。三个等待入口：

| 方法 | 行为 |
|---|---|
| `Wait()` `:116` | 先 `WaitStart()`；`Stop` 直接返回 `false`；`do { if(Stop) return false; Thread.Sleep(5); } while(!signalEvent.WaitOne(recycleTime))` |
| `Wait(int outTime)` `:153` | 同名重载，但**最后一行的 `WaitOne` 仍传 `this.recycleTime`，`outTime` 参数完全没被使用**（`:168`）——见第 8 节 |
| `WaitSingleStep()` `:175` | 非单步模式直接返回 `false` |
| `static WaitStart()` `:202` | `Stop` → `false`；`Pause` → `Thread.Sleep(20)` 死循环直到非 Pause；否则 `true` |

**硬性约定**（`:112-114` 注释明写）：*"如果设备处于暂停状态，循环阻塞接收信号，如果设备停止则返回 false，所以在启动的时候需要先设置设备状态，再启动线程"* —— 这解释了为什么 `Machine.Start()` 里 `SetState(Working)` 在 `:272`、线程在 `:276` 之后才启动；一旦顺序颠倒，线程一进去就因 `Stop` 返回 `false` 而立刻退出。

`SignalPool`（`SignalPool.cs:10`）的 **23 个**信号全部是 `new Signal(名, 100, mode, false)`，按 `EventResetMode` 分两类：

### 5.3 排序矩阵：`WorkProcessEnum` × `WorkProcessModuleEnum`

`WorkProcessEnum`（`ProcessDomain.cs:379`）`TransportFirst`（框架优先）/ `SubstrateFirst`（基板优先）/ `ModuleFirst`（基岛优先）/ `BondPositionFirst`（焊点优先）；`WorkProcessModuleEnum`（`:409`）`StepFirst`（步骤优先）/ `PositionFirst`（位置优先）。二者组合出 8 个方法，`S2ActionNodeController.cs:182-233` 的 `switch` 是唯一分派点。**8 个方法的骨架高度重复**，都遵循：

```
1. TransportPreActionNodes → ActionNodeMessage(name, 0, 0, null)      （substrate/module 都为 0 表示「整机级动作」）
2. SubstrateActonNodes     → (name, 基板序号 i+1, 0, null)
3. ModuleActonNodes        → (name, i+1, 基岛序号 j+1, null)
4. BondPositionActonNodes  → (name, i+1, j+1, 焊点所属步骤名)
5. 步骤本体                → GetActionNodeMessageByProcess(...)
```

差别只在**循环嵌套层次与顺序**（谁在最外层）以及**是否使用 `MathHelper.GetCycleList` 做循环分组**：
- `TransportFirst` 两方法用 `GetCycleList(SubstrateCount, workCycleNumber)` 把基板分组轮转（`:252` / `:329`）；
- `SubstrateFirst` 两方法用 `GetCycleList(ModuleCount, ...)` 把基岛分组轮转（`:406` / `:472`）；
- `ModuleFirst` / `BondPositionFirst` 四方法用朴素双重循环。
- `workCycleNumber` 在 `IsWorkCycleNumber == false` 时被覆写为 `SubstrateCount`（`:247-250`、`:324-327`）或 `ModuleCount`（`:401-404`、`:467-470`）。

`BondPositionFirsAndPositionFirst`（`:664`）是唯一一个把 `GetWorkBondPosition()` 放进内层循环、并用 `bondPositionProcessSteps.Remove(...)` 保证「位置优先」的方法（`:685-697`）；点胶侧同位置在 `S1ActionNodeController.cs:678-690`。

**步骤 → 动作的匹配靠字符串**：`ActionNodeMessage`（`Infrastructure/Models/CommonModels/ActionNodeMessage.cs:12`）只有 4 个字段 `ActionNodeName` / `Substrate` / `Module` / `ProcessStepName` / `Finished`（`:39-59`）。`ProcessStepName` 是「执行基岛所在的行」，用于在同一 (基板,基岛) 内区分不同步骤产生的同名动作节点。

### 5.4 换向机（`IsOppositeSex`）与禁用项过滤

- `RemoveOtherStep()`（`S2ActionNodeController.cs:1498`，点胶侧 `S1ActionNodeController.cs:887`）：仅换向机生效。它按 `OppositeSexConfiguration.OppositeSexConfigs.DownConfigs[基板-1].DownConfigs[基岛-1].DownConfigs` 逐层校验，若该焊点不在对应层级配置里就 `RemoveAt(i); i--`。**`i--` 配合 `RemoveAt` 是本文件最常见的遍历删除手法**（另见 `:1515`、`:1528`、`:1545`、`:1597`、`:1611`、`:1620`）。

### 5.5 相对贴片重排 `SortRelativeBond()`

`S2ActionNodeController.cs:1440`：找出 `SingleBpPositionConfig.RelativeBondPosition == true` 的焊点（`:1443-1444`）→ 删掉这些步骤的所有 `BondPositionVisionActionNode`（`:1471-1472`）→ 在每个对应步骤的 `PickActionNode` **之前**重新插入一个 `BondPositionVisionActionNode`（`:1476-1492`，`Insert(i, ...)` 后 `i++` 跳过）。原因是相对贴片的焊点必须等前一颗固晶完才能拍照，所以拍照时机要挪到取片之前。

## 8. 注意事项与风险

### 8.1 明确的 Bug / 死代码

1. **`Signal.Wait(int outTime)` 的超时参数被忽略**：`Signal.cs:168` 写的是 `return this.signalEvent.WaitOne(this.recycleTime);`，`outTime` 从未参与计算。任何指望该重载做超时控制的调用都不会生效。
2. **`Machine.ResetAlarm()` / `SetStopStateAlarm()` 的空集合判断写反**：`Machine.cs:171` 与 `:188` 都是 `if (hardwaresByType == null || hardwaresByType.Any<Alarmer>())` —— **集合存在且非空时才进入分支、空集合时反而跳过**，紧接着 `hardwaresByType[0]`。对比 `HardWareCheck.cs:64` 的正确写法 `if (alarmerList == null || !alarmerList.Any<Alarmer>())`，可确认是漏写 `!`。虽然正常机型上报警器一定存在（掩盖了问题），但空集合路径会 `NullReferenceException`/`IndexOutOfRange`。
3. **`S2ActionNodeController.ChangeNameToActionNode()` 的空检查在使用之后**：`:1084` 先 `this.ActionNodes.Find(...)`，`:1086` 才判 `if (this.ActionNodes == null) throw` —— 检查永远不会拦住 NRE。

### 8.3 硬编码与隐式约定

1. **`"Null"` 字符串哨兵**：`SingleProcessStep` 的 `BondPositionName` / `ComponentName` / `DefectName` / `EpoxyNameApplicationName` 都用字符串 `"Null"` 表示「未选择」（`SingleProcessStep.cs:52-67`），全部判定都写成 `!= "Null"` 字面量比较（`S2ActionNodeController.cs:721/855/864`、`S1ActionNodeController.cs:714/723`、`ProcessDomain.cs:64/122/151`）。**若用户把某个焊点/芯片/胶型命名为 `Null`，逻辑会错乱。**UI 的 `LsBondPosition.Items.Add("Null")`（`UcProcessStep.cs:284`）等也印证了这一点。
2. **动作节点名以字符串常量参与控制流**：`"BondActionNode"`（`S2ActionNodeController.cs:1156/1202`）、`"UpLookCorrectionActionNode"` / `"SubstrateCameraCorrectionActionNode"`（`:1056`）、`"BondPositionVisionActionNode"`（`:1472`）、`"PickActionNode"`（`:1481`）；点胶侧 `"S1DispenseMeasureActionNode"` 等（`DispenseWorkTask.cs:133-136`）。这些字面量必须与 `BondActionNodeRepository` / `DispenseActionNodes` 里的 `Name` 严格一致，**重命名动作节点会静默破坏排序**。
3. **`ProcessSteps` 是「每次访问都重算」的 LINQ 属性**：`S2ActionNodeController.cs:92-93`、`S1ActionNodeController.cs:105-106` 每次读取都 `FindAll(it => it.IsEnable)`，而排序方法里在双重/三重循环内多处读取它（如 `:301`、`:382`、`:448`）。虽然正确性无损，但复杂排序下一轮 `Init()` 会产生大量小对象——属性能热点。

### 8.4 并发安全隐患

1. **`Machine.WorkTasks` 是公有可变字段**（`Machine.cs:69`），`IsAllowTaskClosed()`（`:198`）每次调用先 `new List<Task>()` 覆盖它，随后推入 **16 处** `WorkTasks.Add`（`Machine.cs:205`、`208`–`246`）的 `Task` 引用。
   ⚠️ **其中 `:205` 是有条件的**（`System1Domain...DispenseWorkTask`，其前面 `:203` 有 `IsSystem1Configrated` 判断），其余 **15 处无条件** ⇒ **运行时实际是 15 或 16 个，取决于 System1 是否配置**。此法此前写作"15 个"是把 `:205` 那处算漏了。
   若 `UcMainSystem.UIState.cs:388` 之外还有别处读 `WorkTasks`，会读到被覆盖后的瞬时状态。判断本身只检查 `Status == Running`（`:252`），**`WaitToRun`/`Faulted` 也算「已关闭」**。
2. **`MachineStateModel` 是跨线程共享的 POCO，无任何锁**：`IsSingleStepWork` 甚至是一个公有**字段**（`MachineStateModel.cs:122`）而非属性，`Machine.Stop()`（`Machine.Operate.cs:359`）与 UI 线程可能同时读写。
3. **`SetState()` 的读-改-写非原子**（`Machine.StateRelated.cs:54-64`）：先读 `oldState`、再赋值、再写日志，两个线程同时切换状态可能产生顺序错乱的日志或丢失状态变更。
4. **`StartBackGroundThread()` 的守卫非原子**（`Machine.Operate.cs:667`）：`if (this.BackGroundThreadThread == null || !this.BackGroundThreadThread.IsAlive)` 在并发调用下可能起两条监控线程。
5. **`EmergencyStop()` 并行停轴**：`Parallel.ForEach(axisList, ...)` + 闭包内 `axis.StopMove(false, true)`（`:388-393`），每个轴的驱动调用并发进入运控卡驱动层，**线程安全性取决于 `AKRS.Galaxy2.Drive`（无源码）**。
6. **`ProcessSteps` / `WorkMessages` 无锁**：排序在 `Machine.Start()`（UI 线程调用）里完成，消费在 `BondTask` 线程里进行；`Finish()`、`SetActionNodeReWork()`、`InitCurrentMessage()` 由动作节点在业务线程调用。**只要不在自动运行中重新 `Init()`，当前实现是安全的**；但 `UcProcessStep` 可以在任意时刻 `ProcessDomain.Save()`（`UcProcessStep.cs:366` 等），保存的是 `ProcessSteps` 而非 `WorkMessages`，暂不冲突。
7. **`Machine.OpenCompensate/CloseCompensate` 内部 `new BondModule()`**（`Machine.Operate.cs:594/619`）：每次回零都新建模块对象去取轴（`GetHardware` 是仓库查找，不算昂贵），但这是「门面里直接 new 业务模块」的耦合写法。
